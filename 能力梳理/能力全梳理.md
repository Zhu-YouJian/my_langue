## 十、关键洞察

### Tenth 的核心优势（已完成且做得好的）

1. **语言核心管线完整**：Lexer → Parser → HIR → VM/解释器/WASM 全通
2. **自举成功**：Tenth 编译器由 Tenth 编写
3. **自动微分可用**：28 算子全链路 backward
4. **神经网络标准库**：从 Linear 到 Transformer 覆盖完整
5. **工具链脚手架**：LSP + 包管理器 + REPL

### 最关键的缺口（按影响排序）

**第一梯队（不做就无法称为"AI 语言"）：**

1. 编译期 Shape 检查 — 唯一护城河
2. GPU 实际算子 — 没有 GPU 就不能训练真实模型
3. ~~f32 张量 — f64 在 AI 中不可接受~~（已解决，见 §5.1 多精度张量；f32 Phase 1-5 已完成双侧对齐，残余不对称见 `docs/f32-f64-parity-roadmap.md`）
4. ~~异步/并发 — 长训练需要~~（已部分解决，Phase 1 + Phase 2 完成：`async fn`/`await`/`spawn` 语法 + `Type::Future` + VM `Op::Await`/`Op::Spawn`/`Op::Yield` + `run_scheduler` 协作式调度器 + `ready_queue`/`suspended` 双队列 + 每任务独立 Frame 栈 + 3 个 async I/O native（`async_sleep_ms`/`async_tcp_read`/`async_tcp_write`）用 `std::thread` + mpsc + thread_local 实现；**Phase 3 遗留**：状态机 lower pass、WASM Future 支持、yield 语法层关键字、spawn 真并行；详见 §1.3 yield/协程、§3 协程/绿色线程与 async runtime、§4.4 异步 I/O 条目）

**第二梯队（不做就无法称为"通用语言"）：**

5. ~~网络/HTTP — 最基础的通用能力~~（已解决，2026-07-07 Stage 1-4 完成：`std::io`/`std::env`/`std::net`/`std::http` 四模块 13 个 native，覆盖 stderr/stdin/env/exit/TCP 客户端/HTTP 客户端；详见 §4.4/§4.5/§4.7）
6. 数据库驱动 — 数据驱动应用必需
7. ~~正则表达式 — 文本处理刚需~~（已解决，2026-07-08 实现：基于 Rust `regex = "1"` crate，6 个 native（`regex_compile`/`regex_match`/`regex_find`/`regex_find_all`/`regex_replace`/`regex_split`）+ `std/regex.th` 6 个 wrapper；handle table 模式与 `tcp_streams` 一致，VM + 解释器双侧注册；详见 §4.2 正则表达式条目）
8. FFI — 复用现有生态的唯一途径
9. ~~元组类型 — 语言基础类型缺失~~（已解决，2026-07-08 全管线实现：`Value::Tuple` + `Type::Tuple` + `ExprKind::Tuple`/`Pattern::Tuple` + 4 个 VM Op（MakeTuple/IsTuple/TupleGet/Try, opcode 49-52）；支持创建/解构/match/函数返回多值；空元组 `()` 编译为 `Value::Unit` 向后兼容；详见 §1.2 元组类型条目，`tuple_test.rs` 12 项测试覆盖）
10. ~~异常处理 / `?` 操作符 — 错误处理太原始~~（已解决，2026-07-08 `?` 操作符全管线实现：方案 B 新增 `Op::Try` 指令，从 `Result<T>` 提取 T，VM 通过 frame 恢复实现 early return，解释器通过 `TryPropagate` 实现错误传播；`try` 关键字保留为未来异常处理机制预留；`try_operator_test.rs` 12 项测试覆盖；详见 §1.3 try 表达式/`?` 操作符条目）

**第三梯队（不做就无法形成"生态"）：**

11. 包注册中心 — tenthpm 没有中央仓库就是空壳
12. VSCode 扩展 — 没有 IDE 集成就没有用户
13. 在线 Playground — 降低试用门槛
14. 测试框架（Tenth 侧）— 用户无法写测试
15. 文档生成 — 标准库无 API 文档

### 总体评估

这个项目完成度约 30%，但**已完成的 30% 是最难的部分**（编译器前端+VM+自举+自动微分）。剩下的 70% 更多是工程量而非技术突破——但工程量本身就是巨大的。
