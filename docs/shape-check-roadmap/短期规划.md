## 当前能力边界（基于代码证据）

| 现状 | 证据 | 影响 |
|------|------|------|
| 类型注解不强制 | `hir/lower/lower_stmt.rs:17-22` — `type_ann` 直接覆盖 `init.ty`，不比较 | `let x: Tensor[f64, 3, 4] = zeros(2, 3)` **不报错** |
| 跨分支不检查 | 搜索 `branch.*shape` / `if.*else.*type` 无匹配 | `if cond { zeros(3,4) } else { zeros(5,6) }` 不报错 |
| 库函数 shape 失效 | `std/nn/activations.th:5-10` 全用 `Tensor[f64, ..]` | 标准库是 shape 检查的"盲区" |
| 跨函数 shape 丢失 | `fn make() -> Tensor[f64, ..]` 调用方只拿到 `[Any]` | 函数边界切断 shape 流 |

**核心判断**：当前 shape 检查是"表达式局部检查"，不是"程序全局检查"。本阶段的目标是把局部性扩展到全局性。

## 方向 1：类型注解强制化

**问题**：`let x: Tensor[f64, 3, 4] = zeros(2, 3)` 静默通过，注解被忽略。

**方案**：注解与推断 shape 不匹配时报错。在 `lower_stmt.rs:19` 加 `check_annotation_compat(type_ann, init.ty)`。

**价值**：
- 用户能显式标注约束，让动态 shape 代码也享受检查
- 函数参数注解（已工作）+ let 注解（未工作）形成完整约束网络
- 实现成本低，立即补上最明显的漏洞

**ROI**：⭐⭐⭐⭐⭐（小工作量，立即见效）

**验收标准**：
- `let x: Tensor[f64, 3, 4] = zeros(2, 3)` 编译期报错
- `let x: Tensor[f64, 3, 4] = zeros(3, 4)` 编译通过
- `let x: Tensor[f64, ..] = zeros(3, 4)` 编译通过（`..` 不约束）

---

## 方向 2：跨函数 shape 求解

**问题**：`fn make() -> Tensor[f64, ..] { zeros(3,4) }` 调用方拿不到 [3,4]。

**方案**：函数体 lower 时记录返回表达式的精确 shape，调用方用它覆盖签名 shape。

**难点**：
- 多 return 路径需汇聚（join）—— 取各分支 shape 的公共信息
- 递归函数需不动点
- 泛型函数需实例化

**价值**：
- 库函数 shape 传播（`fn weight() -> Tensor[f64, ..] { randn(3, 4) }` 调用方拿到 [3,4]）
- Tenth 作为 AI 原生语言的核心卖点：模型定义的 shape 链路自动检查

**ROI**：⭐⭐⭐⭐（中工作量，但解决"函数边界"这个最大盲区）

**验收标准**：
- `fn make() -> Tensor[f64, ..] { zeros(3, 4) }` 调用方 `let x = make()` 拿到 `[Known(3), Known(4)]`
- 多 return 分支汇聚到公共 shape（兼容分支不报错，不兼容分支报错）
- 标准库函数 shape 能跨调用传播

---

## 方向 3：标准库符号维度标注

**问题**：`activations.th` 等全用 `Tensor[f64, ..]`，shape 检查在库边界失效。

**方案**：关键库函数改用符号维度。

```tenth
// 当前
fn linear(x: Tensor[f64, ..], w: Tensor[f64, ..]) -> Tensor[f64, ..] { x.matmul(w) }

// 深化后
fn linear(x: Tensor[f64, M, K], w: Tensor[f64, K, N]) -> Tensor[f64, M, N] { x.matmul(w) }
```

**价值**：
- 用户调用 `linear(zeros(3,4), zeros(5,6))` 立即报错（K=4 ≠ 5）
- Tenth 标准库成为"shape 自文档化"的范例
- 实现成本：仅需改标准库签名，零编译器改动

**ROI**：⭐⭐⭐⭐⭐（纯文档级工作量，立竿见影）

**验收标准**：
- `std/nn` 关键模块（attention/linear/feedforward/transformer）签名改用符号维度
- 错误的库调用在编译期报错
- 全量 stdlib_test 无回归

---

## 方向 4：跨分支 shape 一致性

**问题**：`if cond { zeros(3,4) } else { zeros(5,6) }` 不报错。

**方案**：if/else、match 各分支返回 shape 必须兼容（用 `broadcast_shapes` 的 join 语义）。

**价值**：
- 提前发现逻辑错误（如 attention 中忘记 transpose 导致两个分支 shape 不同）

**ROI**：⭐⭐⭐（低成本，但场景频率中等）

**验收标准**：
- `if cond { zeros(3,4) } else { zeros(5,6) }` 编译期报错
- `if cond { zeros(3,4) } else { zeros(3,4) }` 编译通过
- `if cond { zeros(3,4) } else { zeros(1,4) }` 编译通过（广播兼容）

---

## 推荐推进顺序

按 ROI 排序：

1. **方向 3（标准库标注）** — 纯文档级工作量，立竿见影
2. **方向 1（注解强制化）** — 补最明显漏洞，小工作量
3. **方向 4（跨分支一致性）** — 低成本扩展检查覆盖
4. **方向 2（跨函数求解）** — 中等工作量，解决函数边界盲区

前三者合力把 shape 检查从"表达式局部"提升到"程序全局"。方向 2 是终极目标但成本较高，建议在前三者完成后推进。

## 与战略规划的关系

本阶段是"补漏洞"，把 shape 检查的覆盖面补全。战略规划（见 `战略规划.md`）是"建护城河"，让 shape 检查成为 Tenth 真正区别于 PyTorch/JAX 的核心技术能力。

短期规划完成后，战略规划的方向 A（Autograd Shape 验证）、D（内存/算力预估）可以直接建立在全局 shape 流之上。
