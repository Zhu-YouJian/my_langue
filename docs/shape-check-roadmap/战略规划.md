# 编译期 Shape 检查 — 战略规划

> 让 shape 检查成为 Tenth 真正区别于 PyTorch/JAX 的核心技术能力
>
> 本文档的方向都是"护城河级"深化——解决 AI 框架长期没解决或解决得不好的问题，且 Tenth 作为编译型语言有结构性优势
>
> 创建：2026-07-01

---

## 战略定位

**核心命题**：当前 shape 检查是"表达式局部检查"，PyTorch/JAX 也都有（JAX 的 `check_shading` 更强）。要成为护城河，必须做到它们做不到的事：

1. **反向 shape 静态验证**（JAX 没做好）
2. **shape 作为代数类型**（PyTorch 没做）
3. **编译期内存/算力预估**（无竞品）
4. **模型 schema 静态验证**（PyTorch 结构性短板）
5. **shape 驱动的 JIT 特化**（对标 torch.compile，更早阶段做）

这些方向让 shape 检查从"对不对"升级到"贵不贵"、"反向对不对"、"模型组装对不对"，是 AI 原生语言的真正体现。

---

## 方向 A：Autograd Shape 静态验证

### 观察的事实

`runtime/autodiff.rs:344` `TapeOp::MatMul` 反向传播用 `unbroadcast` 把梯度 squeeze 回输入 shape —— **反向传播在运行时才发现 shape 不匹配**，且靠 silent squeeze 掩盖错误。

silent squeeze 是 AI 框架 bug 的常见来源：梯度被错误广播后悄悄 reshape 回去，loss 不报错但训练不收敛。开发者很难定位。

### 深化方案

编译期推导每个算子的反向 shape 规则，与前向 shape 联合检查。

```tenth
fn loss(logits: Tensor[f64, B, V], targets: Tensor[f64, B]) -> f64 {
    logits.cross_entropy(targets)  // 当前：检查前向
}
// 深化后：编译期验证 ∂loss/∂logits 的 shape == [B, V]
//        ∂loss/∂targets 的 shape == [B]
//        若用户写错 targets shape（如 [V, B]），编译期即报错
```

### 实现路径

1. 每个 `TapeOp` 配一个 `backward_shape_fn(forward_inputs, forward_output) -> Vec<Shape>`
2. lower 时对带 `grad` 标记的函数做反向 shape 传播
3. 若反向 shape 与前向输入 shape 不兼容，编译期报错

### 护城河价值

**这是 JAX 都没做好的事**。JAX 的 `check_shading` 只检查前向，反向 shape 错误靠运行时 NaN 报错。Tenth 编译期就拦下来，是真实的"AI 原生"优势。

### 评估

- 护城河：极强（JAX 没做好）
- 实用价值：高（训练 bug 早发现，silent squeeze 是真实痛点）
- 可行性：中（需为每个 TapeOp 配反向 shape 规则）
- **综合 ROI：⭐⭐⭐⭐⭐**

## 方向 B：Shape 代数求解器

### 观察的事实

当前 shape 检查是**等值匹配**（K == K），但真实 AI 代码大量需要**代数推理**：

```tenth
let x: Tensor[f64, M, N] = ...;
let y = x.reshape(M * N);      // 当前：报 Any，因 M*N 不是字面量
let z = x.reshape(M, N);        // 当前：报 Any
let w = x.flatten().reshape(M, N);  // 当前：报 Any，且无法验证 [M*N] reshape 回 [M,N] 合法
```

### 深化方案

shape 不仅是 Dim 值，而是**符号表达式**。`Dim` 扩展为：

```rust
enum Dim {
    Known(i64),
    Symbol(String),
    Any,
    // 新增（受限子集，见下方注意事项）：
    Mul(Box<Dim>, Box<Dim>),      // M * N
    Add(Box<Dim>, Box<Dim>),      // M + N（cat 后）
    Div(Box<Dim>, i64),            // M / 4（split）
    Eq(Box<Dim>, Box<Dim>),        // 约束：M == N
}
```

shape 检查变成**线性算术约束求解**（SAT 可解，NP 但实例小）。

### ⚠️ 重要注意事项：编译期成本可控性

**本方向已从 ⭐⭐⭐⭐⭐ 降级为 ⭐⭐⭐**，原因是编译期成本不可控，需严格限定约束类型。

**根本问题**：约束求解可能 NP-hard，实例大时拖慢编译。Tenth 的核心卖点之一是自举 ~0.2s（工作规范明确"不超过 1s"），引入不可控的求解器会破坏这一保证。

**必须遵守的限制**：

1. **只做"检查"，不做"求解"**
   - ✅ 允许：给定 `M*N` 和 `M`、`N`，验证 `flatten().reshape(M, N)` 合法（O(1) 代入比较）
   - ❌ 禁止：给定 `X` 和 `M*N == X`，搜索满足的 `M`、`N`（NP 搜索）

2. **只支持线性约束子集**
   - ✅ 允许：`M + N`（cat 后）、`M * N`（flatten，但 M、N 必须已知）、`M / k`（k 为字面量）
   - ❌ 禁止：非线性约束（如 `M * N == K * L` 需因式分解）、约束传播链（A=B=C=...）

3. **单点验证，不传播**
   - ✅ 允许：`x.reshape(M, N)` 时检查 `M * N == x.numel()`（一次比较）
   - ❌ 禁止：跨函数建立全局约束图并传播

4. **超时保护**
   - 任何约束检查超过 N 条链路（如 10）即放弃，回退到 `Any`
   - 永远不允许编译器因约束分析 hang

5. **可选而非强制**
   - 重型约束分析应做成 `--strict-shapes` 模式，默认关闭
   - 默认编译保持快速（"检查"类工作），重型分析用户主动开启

**判断原则**：shape 检查是 O(n) 的"检查"，永远值得做；shape 求解是可能 NP 的"搜索"，必须限定为 O(1) 的代入验证。如果某个场景无法 O(1) 验证，宁可报 `Any` 放弃，也不要引入求解器。

### 护城河价值

PyTorch 的 `torch.compile` 用 symbolic shapes 做这个，但运行时。Tenth 在编译期做，且能跨函数传播 —— 真正的"shape 作为类型"而非"shape 作为注解"。

**但需诚实承认**：在受限子集下（只检查不求解），护城河价值从"极强"降为"中强"——能验证用户写的约束是否自洽，但不能自动推导未知约束。这仍优于 PyTorch（运行时才发现），但不如完整求解器革命性。

### 真实便利

用户能写 `fn attention(x: Tensor[f64, M, K]) -> Tensor[f64, M, K]` 而 K 通过 reshape/permute 链路自动传播，无需手写 `assert`。

**但需诚实承认**：在受限子集下，"自动传播"仅限于 O(1) 可验证的链路。复杂场景（如 `x.flatten().reshape(?, ?)` 需因式分解）仍需用户显式标注。

### 评估

- 护城河：中强（受限子集下，优于 PyTorch 但非革命性）
- 实用价值：中（reshape/cat/split 链路部分自动，复杂场景仍需手写）
- 可行性：中（受限子集实现成本可控，但边界设计需谨慎）
- **综合 ROI：⭐⭐⭐**（已从 ⭐⭐⭐⭐⭐ 降级，编译期成本不可控是核心风险）

### 降级理由总结

原评级 ⭐⭐⭐⭐⭐ 基于乐观假设"实例小，NP 不成问题"。但：
1. 编译期成本不可控与 Tenth 自举 ~0.2s 的核心保证冲突
2. NP 求解器在恶意输入（如用户代码大量使用符号维度）下可能 hang
3. 受限子集（只检查不求解）的价值显著低于完整求解器
4. 工作规范的"禁止破坏自举三路径"要求编译期成本必须可预测

基于"检查多做、求解少做"的原则，本方向应限定为线性约束的 O(1) 代入验证，而非通用求解器。

## 方向 C：Model Shape Schema 编译期验证

### 观察的事实

当前模型定义全靠运行时报错。`Transformer` 的 `q/k/v` shape 不匹配要到第一次 forward 才崩。

### 深化方案

把 `struct` + `impl` 中的方法签名当作"shape schema"，编译期对模型组装做类型检查。

```tenth
struct Attention {
    q_proj: Linear,   // Linear: [D, D]
    k_proj: Linear,   // Linear: [D, D]
}

impl Attention {
    fn forward(self, x: Tensor[f64, B, S, D]) -> Tensor[f64, B, S, D] {
        let q = self.q_proj(x);   // [B, S, D]
        let k = self.k_proj(x);   // [B, S, D]
        let kT = k.transpose();   // [B, D, S]  ← 2D transpose 不够，需 batched
        q.matmul(kT)              // 编译期报错：[B,S,D] @ [B,D,S] 需 batched matmul
    }
}
```

### 护城河价值

**PyTorch 的结构性短板**（动态图无法静态验证模型）。Tenth 作为编译型 AI 语言天然能做。一旦做好，"改一行模型代码，编译器告诉你哪里 shape 错"就是真实卖点。

### 实现路径

1. struct 字段类型支持 Tensor shape
2. impl 方法的 forward 签名作为 contract
3. 模型组装时（`make_transformer()`）编译期走一遍 forward

### 前置依赖

需先完成短期规划的方向 2（跨函数 shape 求解）。

### 评估

- 护城河：强（PyTorch 结构短板）
- 实用价值：极高（模型开发核心场景）
- 可行性：低（依赖跨函数 shape + 完整 batched 算子）
- **综合 ROI：⭐⭐⭐⭐**

## 方向 D：编译期内存/算力预估

### 观察的事实

AI 开发的真实痛点不是 shape 错误，而是 **OOM** 和**慢**。当前 shape 检查只判断"对不对"，不判断"贵不贵"。

### 深化方案

shape 已知 → 元素总数已知 → 显存/算力预估。

```tenth
let x = zeros(1024, 1024, 1024);   // 编译期警告：1B 元素 * 8 bytes = 8GB
let y = x.matmul(other);            // 编译期提示：~2G FLOPs
```

### 护城河价值

**没有任何主流 AI 框架做这个**。PyTorch 要等 CUDA OOM 才报错，JAX 的 `jax.check_shading` 只看 sharding 不看绝对量。Tenth 在编译期给开发者"这个 tensor 多大、这步多贵"的预判，是真实开发效率提升。

### 真实便利

- 调试时不用反复跑崩才知道显存不够
- code review 时编译器自动标注"这步很贵"
- 训练脚本启动前编译期预估总显存

### 实现路径

1. shape 已知时计算 `numel = product(dims)`
2. 对超大 tensor（如 > 1G elements）发编译期 warning
3. 对 matmul/conv 估算 FLOPs（M*K*N 次乘加）
4. 可选：函数级总显存预估（所有 live tensor 之和）

### 评估

- 护城河：强（无竞品）
- 实用价值：极高（每天用得到）
- 可行性：高（shape 已知即可算）
- **综合 ROI：⭐⭐⭐⭐⭐**

## 方向 E：Shape 驱动的算子自动特化

### 观察的事实

当前 matmul 在运行时分支处理 2D/batched/稀疏。JIT 路径无法利用编译期 shape 生成特化代码。

### 深化方案

编译期 shape 已知 → JIT 生成特化 kernel。

```tenth
fn forward(x: Tensor[f64, B, S, D]) -> Tensor[f64, B, S, D] {
    // 编译期已知 4D → JIT 生成 batched matmul 而非运行时分支
    // 编译期已知 D=128 → JIT 内联常数维度循环展开
}
```

### 护城河价值

这是 **torch.compile + Inductor** 的核心价值，但 Tenth 能在更早阶段（HIR→JIT）做，因 shape 是类型而非运行时属性。理论上能生成比 PyTorch 2.0 更紧的代码。

### 实现路径

JIT 路径从 HIR 读 `Type::Tensor.dims`，若全 `Known` 则生成特化 kernel（无运行时 shape 分支、常数边界循环）。

### 评估

- 护城河：强（对标 torch.compile）
- 实用价值：高（性能）
- 可行性：低（JIT 改造大）
- **综合 ROI：⭐⭐⭐**

## 方向 F：张量关系调试器（Tensor Relationship Debugger）

### 战略起源

本方向源自一次头脑风暴：**所有 AI 框架的报错都是"位置导向"的（哪一行错了），但数值计算的 bug 经常是"关系导向"的（两个张量的依赖关系错了）。** 错误源头和错误表现位置在计算图中相距很远——前向第 3 步的 reshape 错误，可能到反向第 30 步才以 grad shape 不匹配的形式爆出来。现有框架让用户自己沿栈回溯，体验极差。

**核心命题**：把调试单位从"代码行"换成"数据依赖边"。报错形式从"`mat1 and mat2 shapes cannot be multiplied (3x8 and 4x8)` + 栈"升级为"**张量 a 和张量 b 之间出错了：出错类型：某某**"。

### 观察的事实

| 框架 | 报错形式 | 盲区 |
|------|---------|------|
| PyTorch | `RuntimeError: mat1 and mat2 shapes cannot be multiplied` + 栈 | 告诉你"哪一行错"，但不告诉你"为什么这一行会变成 3x8"——要你自己往上溯 |
| JAX | trace 报错 + 抽象值 | 显示值流，但仍以位置为中心 |
| TensorFlow | 图节点名 + shape | 节点名是机器生成的，人难读 |

**现有所有 AI 框架都没有"关系导向"的报错**。这是调试体验的结构性盲区。

### 与 Tenth 现有架构的天然契合

Tenth 有三个已存在的基础设施，让这个想法比在其他语言里容易实现：

1. **HIR 是静态 DAG**：编译型语言天然有完整依赖图，PyTorch 是动态图拿不到。这是 Tenth 相对 PyTorch 的结构性优势。
2. **TapeOp 是运行时 DAG**：`runtime/autodiff.rs` 的反向传播本身就在遍历依赖图。报错时"反向走到哪个节点、上游是谁"这些信息**已经存在**，只是没暴露给用户。
3. **护城河 A 已经在做"反向 shape 检查"**：消除 silent squeeze 后，错误信息是"acc_grad shape 不匹配"——这已经是"关系 bug"，只是定位还不够细。本方向是把护城河 A 的报错**升级**：从"节点 X 出错"升级到"节点 a → 节点 b 这条边出错，类型是 shape mismatch"。

换句话说，这个想法**不是从零开始**，是护城河 A 的自然延伸 + Tape 诊断信息的显式化。

### 深化方案

#### 双层架构：静态可达性 + 动态路径定位

| 层 | 能做什么 | 局限 |
|----|---------|------|
| **HIR 静态图**（编译期） | 可达性分析："这个 reshape 会不会影响 loss？" | 拿不到运行时实际 shape |
| **Tape 动态图**（运行时） | 精确 shape/value 路径定位 | 要等运行才报错 |

理想方案是**双层**：编译期做"潜在关系问题"警告（静态可达性 + shape 符号推断），运行时做"精确边定位"。这正好对应 Tenth "检查多做、求解少做"的原则。

#### 张量标识方案（待定）

这是最关键的设计决策：

- **变量名**：用户友好，但同一个变量会被赋值多次（SSA 问题）
- **HIR SSA 值**：精确，但用户看不懂 `%t123`
- **运行时 Tensor 对象 id**：动态精确，但编译期用不了
- **来源 span + 版本号**：`x@line15:v2`——可读且精确，**推荐这个方向**

#### 出错类型分类（创新核心）

"出错类型：某某"看似简单，实则是创新核心。每一类对应一种现有调试地狱：

| 出错类型 | 现有调试体验 | Tenth 关系报错 |
|---------|-------------|----------------|
| **Shape mismatch** | "RuntimeError: 3x8 vs 4x8" 然后你猜 | "a→b 边上 shape 从 [3,8] 变成 [4,8]，根因是 a 上游的 transpose 漏写" |
| **Silent squeeze 试图** | 现有框架静默修正，你根本不知道 | "a→b 边上检测到 1D 被挤压，这通常掩盖了上游 reshape 错误" |
| **Broadcast 失败** | 报错但不说为什么 | "a[3,1] 与 b[1,4] 无法广播，因为 a 的第 0 维来自 c 的 reduce" |
| **Grad shape 漂移** | 反向报错完全找不到前向原因 | "反向到 b 时 grad 是 [4,8]，但 a 期望 [3,8]，前向 a→b 经过 sum(0) 降维" |
| **Dtype 冲突** | 精度丢失找不到源头 | "a(f32)→b(f64) 发生提升，根因是 b 下游有 f64 字面量" |

**最后一行（grad shape 漂移）是杀手级特性**——这是护城河 A 消除 silent squeeze 后，用户最需要的配套诊断。现有框架完全做不到，因为它们没有"前向 shape 流 + 反向 shape 流"的对照。

### 可达矩阵的存储——要小心爆炸

N 个张量的可达矩阵是 O(N²)。对大模型（几万个张量）会爆。但注意：

- 编译期 HIR 的张量节点数远小于运行时（一个 `for` 循环体里的张量是一个节点）
- 实际不需要全量可达矩阵，只需要**错误发生时的反向路径**（从出错节点 BFS 到根）
- 可以用"懒计算"——只在报错时才计算相关子图的可达性

所以"可达矩阵"作为**数据结构**可能不需要常驻，但作为**报错时的查询能力**是必须的。

### 护城河价值

1. **不可替代性**：现有框架架构上做不到（动态图无静态 DAG）。PyTorch/JAX 受限于动态图/trace 架构，做不到编译期关系分析；Tenth 的 HIR+Tape 双层结构是结构性优势。
2. **可感知性**：报错信息是用户每次写 bug 都会看到的，体验差异极其直观。
3. **可演示性**：一个 30 行的"PyTorch 报错 vs Tenth 报错"对比视频就能让人懂。

**而且这个特性对非 AI 场景同样有效**：金融 Greeks 出错时定位"哪个参数影响了哪个 Greek"、物理仿真 IK 出错时定位"哪个关节雅可比行维度不对"——都是同一套关系调试。这与 Tenth 向非 AI 场景扩展的战略方向**天然协同**。

### 与现有护城河的关系

| 护城河 | 关系 |
|--------|------|
| **A. Autograd Shape 验证** | F 是 A 的报错信息升级——A 拦截错误，F 定位错误到"边" |
| **D. 内存/算力预估** | F 可复用 D 的 shape 流信息做根因分析 |
| **B. Shape 代数求解** | F 的"根因是 a 上游的 transpose 漏写"需要 B 的符号传播支持 |

F 不是独立的护城河，而是 A/B/D 的**用户界面层**——把已有的底层信息组织成人类可读的关系报错。这也是它的杠杆所在：实现成本相对低（信息已存在），但体验提升巨大。

### 评估

- 护城河：强（现有框架架构上做不到）
- 实用价值：极高（每次写 bug 都会用到）
- 可行性：中（需设计张量标识方案 + 报错路径选择算法，但底层信息已就绪）
- **综合 ROI：⭐⭐⭐⭐⭐**（信息杠杆高，实现成本相对低，体验提升直观）

### ⚠️ 未决设计问题

本方向目前是**战略级规划**，尚未深入研究。以下问题待调研：

1. **张量标识方案**：`x@line15:v2` 是否足够？用户能否自定义张量"标签"以便报错时更易读？
2. **报错路径选择**：从出错节点到根有多条路径，选哪条展示？最短？最相关？全展示？
3. **编译期 vs 运行时边界**：哪些关系问题能在编译期警告，哪些只能运行时报错？
4. **性能开销**：运行时是否需要额外记录依赖边？还是从 Tape 反推即可？
5. **与现有 shape 检查的集成**：护城河 A/D 的报错如何升级为"关系"形式而不破坏现有 API？

### 实现路径（粗略，待细化）

1. 定义"关系报错"的**信息模型**：张量在图里怎么标识、一条边上携带什么信息、报错时怎么选路径展示
2. 编译期：HIR 依赖图 + 可达性分析 → 潜在关系警告
3. 运行时：Tape 依赖边 + shape 流对照 → 精确边定位
4. 报错格式设计 + 用户测试

### 核心洞察

方向 A、D、F 是真正的护城河 —— 它们解决的是 AI 框架长期没解决或解决得不好的问题，且 Tenth 作为编译型语言有结构性优势。

**方向 A 拦截错误，D 预估成本，F 定位错误到"边"**——三者形成完整的"编译期数值正确性保障"体系。F 尤其特殊：它是 A/D 的用户界面层，把已有的底层信息组织成人类可读的关系报错，杠杆极高。

**方向 D 尤其突出**：用编译期 shape 信息换开发者真实的时间，这是"AI 原生语言"最具体的体现。

**方向 F 的战略价值**：报错信息是用户每次写 bug 都会看到的，体验差异极其直观。一个 30 行的"PyTorch 报错 vs Tenth 报错"对比就能让人理解 Tenth 的价值。这是最强的"可演示"护城河。

**方向 B 已降级**：完整求解器的编译期成本不可控，与 Tenth 自举 ~0.2s 的核心保证冲突。应限定为线性约束的 O(1) 代入验证（"检查"而非"求解"），且做成可选的 `--strict-shapes` 模式。

### 编译期成本控制原则

本规划的方向评估新增"编译期成本可控性"维度：

- **"检查"类工作（O(n) 或 O(1)）**：默认开启，永远值得做。包括 shape 等值匹配、内存预估、autograd 反向 shape 规则匹配、关系可达性分析。
- **"求解"类工作（可能 NP）**：默认关闭，可选开启。包括 shape 代数求解、Symbol unify、跨函数约束传播。
- **绝对原则**：任何可能让编译器 hang 的分析必须做成可选 lint pass，不进主编译路径。Tenth 的 ~0.2s 自举保证不可破坏。
- **运行时诊断类工作**：F 的运行时部分属此类，只在报错时触发，不增加正常运行开销。

### 推荐推进路径

方向 A、D、F 可以独立推进且互不依赖，是最低风险的深化起点：

```
短期规划（补漏洞）→ 方向 D（内存预估，独立）→ 方向 A（autograd 验证，独立）
                                     ↓
                              方向 F（关系调试器，A 的报错升级）  ← 战略级，待调研
                                     ↓
                              方向 B（受限代数检查，可选模式）→ 方向 C（model schema）
                                                                       ↓
                                                                方向 E（JIT 特化）
```

方向 B 限定为"受限代数检查"（只做 O(1) 代入验证，不做求解），并作为 `--strict-shapes` 可选模式，不阻塞主路径。

方向 F 标记为"战略级，待调研"——信息模型和报错路径选择算法需先设计验证，再进入实现。
