## 一、概述与用途

本文件回答一个问题：**「Tenth 性能到底怎样」**——以可复现、可引用、结构化的数据给出答案。

**用途**：

1. **纵向回归参照**：版本间同一场景的耗时变化（防"优化了但不知道"）。
2. **三路径对比**：同一场景在 VM / JIT / 解释器上的差异，支撑"默认路径是否真的快"的判断。
3. **能力量级预期**：标量/控制流、张量算子、autodiff、nn/优化器、编译启动五组各自的量级（G6 为三路径对比组）。
4. **外部对照的起点**：当前无外部参照（见 §五），本文件先把 Tenth 自身的绝对数值固定下来。

**不回答**：跨语言/框架的公平对比（无同机、同算法、同口径的外部实现，见 §五）。

**与硬门槛的分工**：`tenth/tests/bench_gate_test.rs` 是**硬回归门槛**（"不许退化"，阈值 fail 即红）；本文件是**基线数据**（"当前是多少"），不设阈值。

## 二、方法论

统一口径（总师契约 v1 + 2026-09-09 方法学修复裁定，全部场景一致）：

| 项 | 口径 |
|----|------|
| 计时器 | Rust 侧 `std::time::Instant`（ns 精度）。**Tenth 源码内不用** `time_now_ms` 做基准计时（毫秒截断不足） |
| 采样 | 每场景 **warm-up 1 次**（排除 JIT 编译/缓存冷启）→ 测量 **5 次** → 报 **min** 与 **median**（**`min` 为跨次/跨机可比统计量**，`median` 反映抖动） |
| 短任务放大 | 张量等短任务内部重复 R 次使单次 ≥10ms，报 **单次耗时 = 总耗时 / R** |
| 正确性前置 | 每场景**先断言结果正确**（与 VM 路径对拍）再计时；结果错直接 fail，禁止"测了个错的" |
| 编译/执行分离 | warm-up 覆盖首次 JIT 编译；编译开销单独由 `jit_compile_share` 报告占比 |
| **进程隔离（规范跑法）** | **每测试一个独立进程**（逐测试 `--ignored --nocapture <test>`；`.github/workflows/perf.yml` 的 for 循环即此口径）。理由：同进程内前一组堆状态会使后续张量算子膨胀 2-3×，长循环满核负载还会降频（见 §七） |
| **路径隔离** | 各组 `jit` 测试内**不跑 VM**；**VM 由 `perf_vm_scenario` 每场景一个独立进程测**（`PERF_VM_SCENARIO=<G>:<name>`；**按组隔离不够**，见 §七）；`interp` 由独立 `perf_interp_reference` 测（**参考路径，仅比值可用**） |
| CPU 预热 | 每组开始前 **~400ms CPU 频率预热** |
| 口径披露 | 每行伴随 `PERF-NOTE`（热态测量 / `min` 为可比统计量 / 跨次跨机不可直接比） |
| 结构化输出 | `PERF\|<group>\|<scenario>\|<path>\|<metric>\|<value>\|<unit>`（value 6 位小数）；辅助行 `PERF-NA\|`（不可用+原因）、`PERF-NOTE\|`（口径/披露） |
| 路径标识 | `vm`（`vm.call`）/ `jit`（`jit::run_jit`，默认路径）/ `interp`（`Interpreter`）/ `cli`（子进程端到端） |
| 不可用场景 | 某场景在某路径不可用（JIT fallback 等）→ 报 **`n/a` + 原因**，**不得静默跳过** |
| 依赖 | **不引入新依赖**（不引入 criterion 等），沿用现有 `#[ignore]` + `--nocapture` 模式 |

**路径含义**：`jit` 是产品默认执行路径（`tenth run` 默认 JIT），因此 `jit` 列是"用户实际感受到的性能"；`vm`/`interp` 列是对照路径（`interp` 绝对值为热态、仅比值可用）。

## 五、与外部参照的差距（已知局限）

**当前无外部对照数据**——这是本基线最重要的已知局限，必须如实标注：

1. **没有跨语言/框架对照**：尚无与 Go / C++ / PyTorch / JAX 等在同一机器、同一算法、同一口径下的实测对照。因此本文件**不能**支撑"Tenth 性能接近 X""比 Y 快/慢 N 倍"之类的外部结论。
2. **`RELEASE_NOTES.md` §三 的 20× / 7.4× 是纵向对比**：它对比的是 Tenth 自身 v0.4.0 基线 → v1.0.0，**不是外部参照**；引用时须写明"相对自身旧版本"。
3. **autodiff / nn 组此前零性能数据**：本巡检（G3/G4）是这两组的首次系统性采集（已回填）。
4. **外部对照的前置条件**（属后续工作，非现状）：固定机器 + 同算法实现 + 同计时口径 + 同数据类型；在此之前任何外部倍数都不可信。

## 六、复现命令

```powershell
# 一次性加 PATH（cargo 未入 PATH；或直接用 %USERPROFILE%\.cargo\bin\cargo.exe）
$env:PATH = "%USERPROFILE%\.cargo\bin;$env:PATH"

# ① 硬回归门槛（本机/专用机，release；阈值 fib(28)<100ms / loop 1e7<200ms / matmul150<20ms）
cargo test --release --manifest-path tenth/Cargo.toml --test bench_gate_test -- --ignored

# ② 既有三场景基线报告（硬门槛套件内的报告工具）
cargo test --release --manifest-path tenth/Cargo.toml --test bench_gate_test bench_report -- --ignored --nocapture

# ③ 全量基线矩阵（G1-G6 + VM/解释器参考组）——规范跑法：每测试一个独立进程
# ③a 分组跑（jit / interp / cli）：每组一个独立进程
foreach ($t in @("perf_g1_scalar_controlflow","perf_g2_tensor_ops","perf_g3_autodiff",
                 "perf_g4_nn_optim","perf_g5_compile_startup","perf_g6_three_path_compare",
                 "perf_interp_reference")) {
  cargo test --release --manifest-path tenth/Cargo.toml --test perf_baseline_test -- --ignored --nocapture $t
}

# ③b VM 参考路径：**每场景一个独立进程**（AUDIT-11.4.52 第二步；按组隔离不够，见 §七）
#     注：不含 G3:tape_overhead —— 它是 autodiff↔手写成对测量 + 派生比值，由 ③a 的
#     perf_g3_autodiff 产出（其 jit/vm 在同一进程内相邻测得），不是单场景。
$vmSpecs = @("G1:fib28","G1:loop_mod_1e7","G1:closure_1e6","G1:method_vec_1e6","G1:tail_rec_1e6",
             "G2:matmul_512","G2:matmul_1024","G2:elementwise_mul_1k","G2:broadcast_add_1k",
             "G2:reduce_sum_1k","G2:transpose_1k",
             "G3:mlp_fwd_bwd","G3:transformer_block_fwd_bwd",
             "G4:linear_fwd_bwd","G4:mha_fwd_bwd","G4:layer_norm_fwd_bwd",
             "G4:softmax_ce_fwd_bwd","G4:adamw_step_1e6",
             "G6:fib28","G6:loop_mod_1e7","G6:matmul_512")
foreach ($s in $vmSpecs) {
  $env:PERF_VM_SCENARIO = $s
  cargo test --release --manifest-path tenth/Cargo.toml --test perf_baseline_test -- --ignored --nocapture perf_vm_scenario
}
```

**CI 接线（软门槛）**：`.github/workflows/perf.yml`（`workflow_dispatch` + 每周一 03:00 UTC `schedule`）按上述**每测试独立进程**的 for 循环跑基线（外加 `bench_gate_test`），输出 job summary + artifact，**仅报告不阻塞**（`continue-on-error`；手动触发可勾选 `strict` 恢复阻塞语义）。**硬阈值在本机 / 专用机执行**（命令 ①）。

**数据更新流程**：重跑命令 ③a + ③b → 以日志中的 `PERF|...` 行为准回填 §四，并同步更新文件头与 §三 的 as-of 日期；数字只改本文件（SSOT）。

## 七、局限与噪声说明

### 测量噪声与复现性（2026-09-09 方法学修复）

- **修复前**：同一进程内顺序跑 G1-G6 + interp 参考组——前一组遗留的堆状态使后续张量算子膨胀 **2-3×**（实测 `matmul_512` 安静态 ~6.5ms → 负载态 15-20ms），长循环满核负载还会导致降频 → 数据 **2-4× 膨胀，不可信**。
- **修复后（规范跑法）**：**每测试一个独立进程** + 每组前 ~400ms CPU 频率预热 + `jit` 组内不跑 VM + `interp` 独立参考组 → 总师独立复跑逐场景偏差 **2-8%**（可复现）。
- **同进程内方差来源未定**（堆状态 vs 频率/核心放置），故规范跑法固定为**独立进程**；跨次 / 跨机不可直接比，`min` 为可比统计量。

### VM 参考路径两次修复（2026-09-16，`AUDIT-11.4.52`）—— 为什么 VM 列必须每场景一进程

`vm` 列是本文件历史上**最不可信的一列**。2026-09-16 分两步修复，修复过程本身就是方法学证据（同一 `matmul_512` 场景的 vm 值）：

| 阶段 | 做法 | G2 `matmul_512` vm | G6 `matmul_512` vm |
|------|------|--------------------|--------------------|
| 9/9 原始 | **一个测试跑完全部组**（阶段 1 全部组 JIT → 阶段 2 全部组 VM） | 14.854 ms | 15.568 ms |
| 第一步：按组隔离 | `perf_vm_reference` 拆成「每组一进程」 | **5.488 ms** | 15.830 ms（**组内顺序效应残留**） |
| 第二步：按场景隔离 | `perf_vm_scenario`（`PERF_VM_SCENARIO=<G>:<name>`）「每场景一进程」 | **5.606 ms** | **5.293 ms** |

**判据是「同一场景跨进程是否收敛」**，不是「换跑法数字变了」：`matmul_512` 的 vm 由 14.854 → 5.488 → 5.293，后两者一致（差 5.6%）即收敛。而它**本应 ≈ jit**（两条路径都委托同一个 ndarray dgemm，jit 为 5.482/5.742）⇒ 第二步结果物理正确；G6 的 `jit/vm` 比值也随之由被污染的 0.396 回到 **≈1.05**。

**可迁移的方法学通则**：

1. **VM 长循环的污染远强于 JIT**：按场景隔离后，同场次 G1 的 vm 变化达 **−47% ~ −58%**（`method_vec_1e6` 553.865→233.656、`tail_rec_1e6` 418.337→178.381、`fib28` 368.916→195.056），而 jit 列同场次仅 ±15% ⇒ **JIT 按组隔离够用，VM 必须按场景隔离**。
2. **9/9 发布的 vm 列因此整体偏高**（最高约 2×），本文件已全量重采覆盖；旧值可在 `.agents/tmp/perf_baseline_run_20260909.log` 追溯（历史只追加不回改）。
3. **测试实现的 `ratio_vs_vm_median` 输出行不可直接引用**：它的 jit 分母是 vm 进程内**作为首个测量**的 jit 基线（偏大——实测 G6 `matmul_512` 进程内 7.52ms vs 独立测量 5.74ms）⇒ §四 G6 表的比值一律**由该表单元格 median 自行计算**。
4. **`tape_overhead` 是例外**：它是 autodiff↔手写**成对测量 + 派生比值**，不是单场景，故仍由 `perf_g3_autodiff` 在其进程内相邻测 jit/vm（已在 §四 G3 标注）。

### G2 局部重跑（2026-09-16，`AUDIT-11.4.47` 落地后）—— 两个发现

1. **快路径确实生效（可归因）**：`elementwise_mul_1k`（同 shape）jit **7.110/7.295 → 1.463/1.583 ms**（min/median，**4.86× / 4.61×**）；与 `reduce_sum_1k` 的 jit median 比值 **53.6× → 14.96×**。同场次 jit 列逐场景 `min` 偏差 **<1%**，优于 9/9 记录的 2-8%。
2. **未受影响的场景落在 9/9 的 ±3.6% 内 —— 但会话级偏移可到 10% 量级**：最终全量重采中 `matmul_512` +2.5%、`matmul_1024` +0.03%、`broadcast_add_1k` +3.5%、`transpose_1k` +3.6%（jit min，相对 9/9）；**这些路径本次未被改动**（广播路径 / ndarray dgemm / 视图 / 归约）。**对照证据**：同日更早的一次 G2 局部重跑里，同一批"未被改动"的场景曾整体偏 **+6~13%**（`transpose_1k` +13.1%）——即**单次会话的整机偏移可达 10% 量级**。⇒ 重申 §三：**跨场次绝对值不可直接比较**；判断改动效果必须用**同场次对照场景归一化**（本例归一化后收益 4.4-4.9×，与原始 4.86× 一致，结论稳健）。

### 其他

- **机器噪声**：后台进程、温控降频、调度抖动都会影响绝对值；同时报 `min` 与 `median` 就是为了看抖动幅度（两者差距大 = 该次测量噪声大）。
- **JIT 编译开销**：warm-up 1 次把首次编译排除在测量之外；编译开销本身由 `jit_compile_share`（G5）单独报告，避免"编译慢"被误读成"执行慢"。
- **JIT 混合体如实披露**：G3 `transformer_block_fwd_bwd` / G4 `mha_fwd_bwd` 的 `jit` 列含 VM 内层（recording gate 回退），**不得当作纯 JIT 数据解读**（见 §四 PERF-NOTE）。
- **短任务放大**：张量短任务用内部重复 R 次放大到 ≥10ms 再除以 R，存在常数开销摊薄误差；R 与放大方式属方法学一部分，见 §二。
- **解释器路径不代表默认性能**：`interp` 是 fallback 路径且为热态参考，仅供比值对照。
- **`#[ignore]` 基准不参与普通 `cargo test`**：基准耗时长且仅在 release 有意义，故显式 `#[ignore]`，需 `--ignored` 执行；跳过原因已按工作规范 §七记录于 `MEMO.md`（2026-09-09 条目）。
- **不可用场景如实报告**：JIT fallback 等场景报 `n/a` + 原因，不做"静默跳过"或"用别的路径的数字顶替"。
- **无外部对照**：见 §五。
- **可比性边界**：绝对数值仅同机同构建同跑法可比；跨机比较需重跑。
