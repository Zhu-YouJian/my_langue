## ARCH-1：autodiff × JIT 复合架构

**问题**：训练路径（autodiff）拿不到 JIT 的任何收益。

**证据**：
- `tenth/src/compile/jit/mod.rs` `run_jit` 的 recording 安全门：`vm.is_recording()` 时整体回退 `vm.call`；
- `tenth/src/runtime/vm/mod.rs` `jit_call_chunk` / `jit_call_chunk_spec` 在 recording 期间把用户函数调用退回 VM；
- 本轮基线实测：G3 `transformer_block_fwd_bwd`、G4 `mha_fwd_bwd` 的 callee `mha_block` **`is_compiled=false`**，PERF 行 `jit` 实为"JIT 外壳 + VM 内层"（已发 `PERF-NOTE` 披露）；
- 数据：`transformer_block_fwd_bwd` vm 261-298ms / jit 276-418ms（jit 未获收益，甚至略慢）。

**为什么是架构问题**：不是 bug，而是"JIT 与 tape 写入互斥"的选型结果。对一门宣称 AI 原生的语言，**训练是核心工作负载，却全程走解释器**。

**探讨要点**：
1. recording-aware 代码生成（在 JIT 机器码里发射 tape 写入）；
2. 静态图 / 梯度 IR（前向定义 → 编译出反向）；
3. tape-free 反向模式 / 检查点（checkpointing）的可行性；
4. "训练走 VM、推理走 JIT"是否是**可接受的长期分工**（若接受，需把该边界写进定位叙事与文档）。

**判据（探讨时的验收线）**：
- 训练步（fwd+bwd）的 JIT 覆盖率 ≥ 约定阈值；
- `backward` 相对 `forward` ≤ 3-4×；
- **红线**：JIT 跳过 tape 写入 = 静默错梯度，任何方案必须三路径对拍守护（参照 `tenth/tests/jit_silent_audit_test.rs`）。

## ARCH-2：tensor 内核分层架构

**问题**：逐元素二元算子比归约慢约 **50×**。

**证据**：
- `tenth/src/runtime/tensor/methods.rs` `elementwise_binary`（约 585-657 行）**无条件** `broadcast().to_owned()` 物化全量副本 + `ArrayD::zeros` + 两次 `zip_mut_with`；
- 实测（2026-09-09，1M f64）：`elementwise_mul_1k` ≈ 7-19ms（约 1.1-2 GB/s）vs `reduce_sum_1k` ≈ 0.11-0.27ms（约 38 GB/s）；
- 已登记 `AUDIT-11.4.47`（同轮登记）。

**探讨要点**：
1. 内核分派分层：**同 shape 无拷贝快路径** / 广播路径（惰性 stride 视图）/ in-place 路径；
2. SIMD 与 autovectorization；分块与并行；
3. BLAS 接入（GEMM 当前 33-48 GFLOPS 单线程，接 BLAS 可能再 +2-5×）；
4. **红线**：in-place 与 autodiff tape 的交互（写坏梯度是静默错值）。

**判据**：逐元素算子达到内存带宽 ≥60%；既有 autodiff 对拍套件全绿。

## ARCH-3：类型系统 / 符号维度架构

**问题**：同一函数体内链式两次调用同一 std 泛型函数会**编译期失败**。

**证据**：
- 实测：`let h = linear<f64>(...); let o = linear<f64>(h, ...)` 因符号维度 `[M,N]` 与 `[M,K]` 不统一而报错（探针复现见本轮运行时部报告 §7.3）；
- 已登记 `AUDIT-11.4.46`（同轮登记）；
- 相关既有工作：`Dim::Symbol` 支持（`AUDIT-11.4.13`）、shape 参数一致化（M3.1）。

**探讨要点**：
1. 符号维度的统一表示与传播（泛型实例化后 shape 如何收敛）；
2. 与 `tenthc` 侧 shape 检查的双侧同步（自举一致性）；
3. 与 shape 护城河的边界——**收紧属改进、放宽属破坏**（见 `docs/API冻结清单.md` semver 约定）。

**判据**：链式调用可用，且既有 shape 检查不放松（shape 相关套件全绿）。

## ARCH-4：执行管线整体架构 / AOT 前置

**问题**：没有 AOT 后端，执行管线只有 VM / 热点 JIT / WASM / 解释器四条路。

**证据**：
- 全库无 AOT 机器码入口（无 `target_machine` / `emit_object` 等）；JIT 依赖 Cranelift（Rust）；
- 三路径一致性守护成本可观：`jit_silent_audit_test` 34 项、`jit_consistency_test` 43 项、`jit_error_line_test` 等；
- AOT 是 `2026-09-09-全自举路线冻结与触发条件.md` 重启讨论的**首要前置**。

**探讨要点**：
1. AOT 的目标是什么（冷启动 / 部署分发 / 自举前置 / 性能上限）——不同目标对应不同设计；
2. 与 JIT 的关系（AOT 为主 + JIT 兜底？还是二选一？）；
3. 前置：SIMD / 向量类型 / 内存布局控制 / native ABI 契约；
4. 折中路线：以 WASM 为中介（Tenth → wasm → wasmtime AOT），复用现有 WASM 后端（注意 WASM 后端现存缺口与无 SIMD）。

**判据**：启动前须先做**可行性论证**（数理部 + 编译器部），且不以牺牲三路径一致性为代价。
