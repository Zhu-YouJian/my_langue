# 立 tenth-lens 为「首个官方 Tenth 项目」

- **日期**：2026-09-16
- **状态**：accepted
- **决策者**：用户（拍板）+ 总师（方案）

## 问题 / 背景

两件事在同一时点撞到一起：

**① 编译器缺"观察装备"。** 2026-09-16 实测盘点（总师）：

- 整个 `tenth/src` 里 `dump|disasm|--emit|print_bytecode|print_ast` **0 命中**——无法从 CLI 看进编译器内部；
- CLI 开关只有 `--max-memory`，子命令只有 `build` / `run` / `wasm`；
- `debug_assert` 全仓仅 **5 处**（4 处在 JIT translator），**无 verifier、无 IR 合法性自检**；
- 与之对比，**测试装备很厚**：三路径对拍（`parity_test` 129 / `jit_silent_audit` 34 / `jit_consistency` 43）、自举不动点、`instance_batch`、`fuzz_test`、`error_recovery`、`native_parity`、结构化 `PERF|` 矩阵。

即：**"失败了"有人告诉你，"为什么"没人告诉你**。而 Tenth 是「多后端 + 双侧手写实现」形态，最大的风险正是**静默分歧**，观察装备恰是压制它的主力。2026-09-16 的实例代价：想判断 montecarlo 那段循环走 JIT 还是回退 VM，**从 CLI 问不到**，只能靠计时差反推，且**第一次推错**（后用 `TENTH_NO_VM=1` 对照才发现 JIT 生效、比解释器快 23×）。

**② 需要真实项目来暴露语言短板。** 语言缺陷被"真实需求逼出来"远比"感觉还差点什么"可信；而工具类程序恰好吃 `fs`/`json`/`cli`/`process`/`collections`/`string`/`logging`——覆盖标准库日常面，又不依赖 GPU / 分布式（已跳过部分）。

## 决策

**立 `tenth-lens/`（仓库根级）为「首个官方 Tenth 项目」，用 Tenth 语言编写**，定位为**编译器可观测性工具链**，按三层推进：

| 层 | 内容 | 职责 |
|----|------|------|
| **记录** | 结构化 dump / 执行记录（`tenth-lens/` 消费） | 证据 |
| **观察** | 跨路径差分、内部状态视图 | 显微镜 |
| **守卫** | 不变量与差分断言 | 判决 |

**分层原则（写入项目 README）**：优先做**差分型**守卫（"两处本该一致"），避免断言**具体行为细节**（会随实现演进误报、进而杀死信任）。

**为此在 `工作规范.md` §八 开一个有界例外**：允许**该白名单目录**存放 `.th`（原规则禁止在 `tenth/`、`tenthc/`、`tenth/std/` 之外创建 `.th`）。例外**唯一且有界**——新增例外必须另立决策记录。

**卡住时的规则**：写不出来的地方**不许绕过**，一律 `NEED: <缺少的语言能力>` + 框架预留 + 登记 `AUDIT.md`。项目结束时应顺带产出一份**真实需求驱动的语言缺口清单**。

## 备选方案与理由

| 方案 | 利 | 弊 | 结论 |
|------|----|----|------|
| **A. 只用 Rust 写这个工具** | 立刻能访问编译器内部 | 放弃 dogfooding 收益；语言短板仍靠猜 | ❌ 不取 |
| **B. 放 `tenth/tools/`（不碰 §八）** | 零规约改动 | 定位成"编译器内部子工具"，与"首个官方项目"的示范意图不符 | ❌ 用户否 |
| **C. 先做守卫，后做记录** | 直接压风险 | 没有结构化记录就没有守卫的原料（守卫是消费记录的产物） | ❌ 次序错 |
| **D. 根级 `tenth-lens/` + 有界例外 + 纯 Tenth**（选中） | 工具 + 语言画像 + 缺口清单三得；P0 零 Rust 改动即可跑 | 需改一条规约；项目需长期维护 | ✅ |

**为什么 P0 选「跨路径差分检查器」而不是 dump 工具**：dump 必须有编译器内部访问权（Rust 改动，需全量 + 自举验证），若作为起点会让项目**卡在 P2 才能跑**；而差分检查器只用现成 CLI（`tenth run` / `TENTH_NO_VM=1`），**第一天就能对 `Tenth实例/` 语料产出真结果**，且正是"差分型守卫"的雏形。

## 后果

- **正面**：得到工具；得到语言真实短板的结构化清单；`PERF|` 等既有记录第一次有消费者；把"性能/一致性"排查从"读 Rust 源码 + 靠计时反推"变成"看记录"。
- **负面 / 成本**：新增需长期维护的项目；触及一条既有规约（已用「唯一白名单 + 新例外须另立决策」收口）。
- **风险**：最大风险是**被语言短板卡住而烂尾**。缓解即上面的 `NEED:` + stub 约定——**卡住本身就是产出**。
- **连带动作**：P2 的 Rust 侧只读钩子属编译器改动，须走全量测试 + 自举验证；新增 CLI 开关按 `工作规范` §3.2 第 6 条同步 `docs/语言参考手册.md`。
