## 摘要

本文对 Tenth 语言的泛型实例化机制进行形式化建模与理论分析。Tenth 泛型采用**无 trait bound 求解的单态化**方案：bound 仅在 HIR 中以 `generics_bounds` 字段记录，不参与编译期约束求解；实例化通过纯类型参数替换 `substitute_type` 完成，并按调用点生成 mangled 名字的专用函数副本。本文给出五条主定理：（M1）单态化健全性，证明所有类型参数在实例化前已被显式确定；（M2）每实例化点编译期复杂度为 $O(|T|)$；（M3）二进制体积膨胀上界为 $O(\sum_{i} |T_i|)$；（M4）表达力对比定理，刻画 Tenth 相对 C++ template、Rust trait bound、Java wildcard 的严格包含关系；（M5）bound 字段对健全性的无害性。本文诚实记录三项局限：体积膨胀无共享、表达力弱于 trait bound 求解系统、body 不参与替换的工程差距。

**关键词**：泛型实例化；单态化；类型替换；trait bound 求解；编译期复杂度；表达力对比；Tenth 语言

## 1. 引言

### 1.1 泛型编程的实现谱系

泛型编程的工程实现可沿两个正交维度划分：

- **代码生成方式**：单态化（monomorphization，每类型参数生成专用副本）vs 装箱（boxing，统一擦除类型并以运行时分派）；
- **约束求解方式**：无约束（仅记录）vs 显式求解（trait bound / concept / type class 解算）。

二者组合产生四种典型方案：C++ template（单态化 + concept 求解）、Rust trait bound（单态化 + trait solver 求解）、Java wildcard（装箱 + 擦除、约束部分求解）、Haskell type class（字典传递 + 求解）。

### 1.2 Tenth 的极简方案

Tenth 选择了一个**极小子集**：单态化 + 不求解。其 HIR 中虽然存在 `generics_bounds: HashMap<String, Vec<String>>` 字段（见 [`hir.rs:229`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/hir.rs)），但该字段在实例化时被显式置空（见 [`lower_expr.rs:289`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)），且全代码库无任何位置读取该字段进行约束求解（见 §5.4 的搜索证据）。这相当于 Rust pre-2021 edition trait solver 的一个**严格子集**——保留了 HIR 字段位以备未来扩展，但求解逻辑被刻意省略。

### 1.3 贡献

本文贡献如下：

1. **形式化建模**：将 `substitute_type` 函数抽象为类型替换算子 $\sigma : \text{Type} \times \text{Subst} \to \text{Type}$，并定义单态化流程的语义；
2. **健全性证明（M1）**：证明在 Tenth 的实例化规则下，所有类型参数在实例化前已被显式确定，无需推理；
3. **复杂度分析（M2, M3）**：给出每实例化点编译期开销与二进制体积膨胀的紧上界；
4. **表达力对比（M4）**：通过包含关系刻画 Tenth 与 C++ / Rust / Java 泛型的表达力序；
5. **bound 无害性（M5）**：证明 bound 字段的存在不影响健全性，为未来引入求解留出余地；
6. **诚实披露局限**：体积膨胀、表达力损失、body 不替换等工程差距。

## 2. 背景与相关工作

### 2.1 C++ template：单态化 + 概念

C++ template 采用**两阶段查找**：解析期语法检查 + 实例化期语义检查。C++20 引入 concepts 后，约束求解在实例化前进行（[Sutton & Stroustrup 2011]）。其单态化是**按需触发**的——只有被实际调用的模板实例才会被实例化，但**没有跨翻译单元的去重保证**（依赖链接器 COMDAT 折叠）。表达力极强，但编译期复杂度理论上是图灵完备的（template metaprogramming），不可判定性已被证明（[Veldhuizen 2003]）。

### 2.2 Rust trait bound：单态化 + 求解

Rust 在单态化前进行 trait bound 求解。其 trait solver 在 pre-2021 edition 采用**全局递归回溯**算法，2021 edition 后引入 chalk-based **canonical query** 求解器（[Jung et al. 2021]）。bound 求解是一个**满足性问题**：给定一组 `T: Trait` 约束，寻找实现链。该问题在存在 associated type 时是半可判定的（可能不终止）。Rust 通过递归深度限制保证终止。

### 2.3 Java wildcard：装箱 + 擦除

Java 泛型采用**类型擦除**：编译后所有泛型类型变为 `Object`，通过**自动装箱**处理基本类型。wildcard (`? extends T` / `? super T`) 提供使用点变体，约束在编译期通过**子typing 规则**部分求解，但运行时无类型信息。优势是二进制兼容性，劣势是性能损失（装箱开销）与表达力受限（无法 `new T()`）。

### 2.4 Haskell type class：字典 + 求解

Haskell type class 编译为**字典传递**：每个 type class 实例编译为一个记录函数指针的字典，约束求解在编译期完成（[Wadler & Blott 1989]）。与单态化不同，字典传递是**运行时**分派，但有编译期去重保证。表达力极强（multi-parameter type class + functional dependencies），但约束求解可能不终止（undecidable instances 扩展）。

### 2.5 Swift witness table：单态化 + 求解

Swift protocol witness table 介于 Rust 与 Haskell 之间：泛型默认单态化，但通过 witness table 进行运行时分派（[Swift ABI 2019]）。其特殊性在于**泛型特化优化**是可选的——编译器在不透明类型上保留 witness table 分派，在已知类型上特化。这与 Tenth "无条件单态化"形成对比。

### 2.6 与本文最相关的工作

Tenth 的方案最接近 Rust pre-2021 trait solver 的**子集**——保留了 HIR 字段位但移除了求解逻辑。这一选择在 ML 族语言早期（SML functor）和 Ada generic 中也有先例，但 Tenth 的特殊性在于**为 AI 计算的 dtype 泛型**场景量身定制（见 §7.3）。

## 3. Tenth 泛型形式化

### 3.1 语法层

Tenth 泛型声明语法（见 [`ast.rs:233-236`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/parser/ast.rs) 的 `GenericParam` 结构）：

```
fn foo<T, U>(a: T, b: U) -> U { ... }
fn bar<T: Clone>(a: T) -> T { ... }   // bound 仅记录，不求解
```

形式化定义：

**定义 3.1（泛型参数）**：泛型参数 $p$ 是二元组 $(n, B)$，其中 $n$ 是参数名（字符串），$B = \{b_1, \dots, b_k\}$ 是 bound 集合（字符串集合，表示 trait 名）。

**定义 3.2（泛型函数模板）**：泛型函数模板 $F = (name, \vec{p}, \vec{params}, ret, body)$，其中 $\vec{p} = [(n_1, B_1), \dots, (n_m, B_m)]$ 是泛型参数列表，$\vec{params}$ 是形参列表，$ret$ 是返回类型，$body$ 是函数体。

### 3.2 bound 的"仅记录"语义

Tenth 中 bound 的处理由 `build_generics_bounds` 函数完成（见 [`mod.rs:146-154`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/mod.rs)）：

```rust
pub(super) fn build_generics_bounds(generics: &[ast::GenericParam]) -> HashMap<String, Vec<String>> {
    let mut bounds_map = HashMap::new();
    for gp in generics {
        if !gp.bounds.is_empty() {
            bounds_map.insert(gp.name.name.clone(), gp.bounds.iter().map(|b| b.name.clone()).collect());
        }
    }
    bounds_map
}
```

该函数仅将 AST 中的 `bounds: Vec<Ident>` 转换为 HIR 中的 `Vec<String>`，**无任何求解、无任何验证、无任何分派**。

**关键搜索证据**：对全代码库 `tenth/src/` 执行 grep，`generics_bounds` 字段共出现 7 处（见 §5.4 详细列表），**无一处是读取该字段做约束求解**——全部是构造（注册时）或重置为空（实例化时）。这从实证上证实了"bound 仅记录不求解"。

### 3.3 substitute_type：类型替换算子

`substitute_type` 函数（见 [`mod.rs:126-144`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/mod.rs)）是 Tenth 泛型实例化的核心：

```rust
pub(super) fn substitute_type(ty: &Type, map: &HashMap<String, Type>) -> Type {
    match ty {
        Type::TypeParam { name } => map.get(name).cloned().unwrap_or_else(|| ty.clone()),
        Type::Ref(inner) => Type::Ref(Box::new(substitute_type(inner, map))),
        Type::MutRef(inner) => Type::MutRef(Box::new(substitute_type(inner, map))),
        Type::Tensor { dtype, dims } => Type::Tensor {
            dtype: Box::new(substitute_type(dtype, map)),
            dims: dims.clone(),
        },
        Type::Array(inner) => Type::Array(Box::new(substitute_type(inner, map))),
        Type::Generic { base, args } => Type::Generic {
            base: Box::new(substitute_type(base, map)),
            args: args.iter().map(|t| substitute_type(t, map)).collect(),
        },
        _ => ty.clone(),
    }
}
```

**形式化定义**：

**定义 3.3（类型替换算子）**：给定替换映射 $\sigma : \text{Name} \rightharpoonup \text{Type}$，类型替换算子 $\text{subst} : \text{Type} \times \sigma \to \text{Type}$ 递归定义为：

$$
\text{subst}(\tau, \sigma) = \begin{cases}
\sigma(n) & \tau = \text{TypeParam}(n) \land n \in \text{dom}(\sigma) \\
\tau & \tau = \text{TypeParam}(n) \land n \notin \text{dom}(\sigma) \\
\text{Ref}(\text{subst}(\tau', \sigma)) & \tau = \text{Ref}(\tau') \\
\text{MutRef}(\text{subst}(\tau', \sigma)) & \tau = \text{MutRef}(\tau') \\
\text{Tensor}(\text{subst}(\tau_d, \sigma), \text{dims}) & \tau = \text{Tensor}(\tau_d, \text{dims}) \\
\text{Array}(\text{subst}(\tau', \sigma)) & \tau = \text{Array}(\tau') \\
\text{Generic}(\text{subst}(\tau_b, \sigma), [\text{subst}(\tau_i, \sigma)]) & \tau = \text{Generic}(\tau_b, [\tau_i]) \\
\tau & \text{otherwise (Base, Struct, etc.)}
\end{cases}
$$

**性质 3.1（终止性）**：$\text{subst}(\tau, \sigma)$ 对任意有限类型 $\tau$ 必终止。

**证明**：递归只在 $\tau$ 的语法子树上展开，$\tau$ 是有限项，递归深度等于 $\tau$ 的高度。$\square$

**性质 3.2（恒等性）**：若 $\sigma = \emptyset$（空映射），则 $\text{subst}(\tau, \sigma) = \tau$。

**证明**：对 $\tau$ 结构归纳。TypeParam 情形由 `unwrap_or_else(|| ty.clone())` 直接返回 $\tau$；其他情形由归纳假设保持。$\square$

**性质 3.3（合成的可换性）**：若 $\sigma_1, \sigma_2$ 的定义域不相交，则 $\text{subst}(\text{subst}(\tau, \sigma_1), \sigma_2) = \text{subst}(\text{subst}(\tau, \sigma_2), \sigma_1)$。

**证明**：对 $\tau$ 结构归纳，TypeParam 情形由定义域不相交保证映射结果唯一。$\square$

> **注**：此性质不要求 $\sigma_1, \sigma_2$ 不可换的更一般情形——Tenth 的实例化只使用单层替换（无嵌套替换），故此性质足够。

### 3.4 单态化流程

实例化由 `lower_expr.rs` 的 `GenericCall` 分支处理（见 [`lower_expr.rs:252-308`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）。形式化为算法 $\text{Mono}$：

**算法 Mono**（单态化）：

输入：泛型函数模板 $F = (name, \vec{p}, \vec{params}, ret, body)$，类型实参 $\vec{\tau} = [\tau_1, \dots, \tau_m]$。

1. 构造替换映射 $\sigma = \{n_i \mapsto \tau_i \mid i = 1, \dots, m\}$；
2. 计算 $ret' = \text{subst}(ret, \sigma)$；
3. 计算 $\vec{params}' = [(n_j, \text{subst}(\tau_{p_j}, \sigma)) \mid j]$；
4. 计算 mangled 名 $name^* = \text{mangle}(name, \vec{\tau})$；
5. 若 $name^* \notin \text{Functions}$：
   - 构造实例化函数 $F^* = (name^*, \vec{params}', ret', body)$；
   - **注意**：$body$ 直接 clone，未替换（见 [`lower_expr.rs:287`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs) `body: template.body.clone()`）；
   - 将 $F^*$ 加入 `Functions`（普通函数表）；
6. 生成对 $name^*$ 的普通 `Call`。

**Mangling 规则**：$name^* = name \_ \tau_1 \_ \tau_2 \_ \dots \_ \tau_m$（见 [`lower_expr.rs:276-277`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs) `fold` 实现，用 `_` 拼接类型的 `Display` 字符串）。

## 4. 主定理与证明

### 4.1 定理 M1（单态化健全性）

**定理 M1**：在 Tenth 的实例化规则下，对任意泛型函数 $F$ 与类型实参 $\vec{\tau}$，所有类型参数在实例化前已被显式确定，无需任何推理或求解。

**前置条件**：
- (C1) 调用点是 `GenericCall`，显式提供类型实参 $\vec{\tau}$；
- (C2) $|\vec{\tau}| = |\vec{p}|$（实参数量等于形参数量）；
- (C3) $\vec{\tau}$ 中每个 $\tau_i$ 是**具体类型**（非 TypeParam）。

**证明**：

由算法 Mono 步骤 1，$\sigma$ 完全由调用点显式提供。我们需证：实例化后函数 $F^*$ 中不存在自由 TypeParam。

**引理 M1.1**（替换消解性）：若 $\sigma$ 的定义域覆盖 $\tau$ 中所有 TypeParam，且 $\sigma$ 的值均为具体类型，则 $\text{subst}(\tau, \sigma)$ 不含 TypeParam。

**引理 M1.1 证明**：对 $\tau$ 结构归纳：
- TypeParam($n$)：$n \in \text{dom}(\sigma)$，$\sigma(n)$ 是具体类型，结论成立；
- Ref / MutRef / Array / Tensor / Generic：由归纳假设，子类型不含 TypeParam，故复合类型不含 TypeParam；
- 其他情形（Base / Struct 等）：本身不含 TypeParam。

$\square$

**主证明**：

由 (C1)(C2)(C3)，$\sigma$ 覆盖 $\vec{p}$ 中所有参数名，且值为具体类型。由引理 M1.1，$ret' = \text{subst}(ret, \sigma)$ 与 $\vec{params}'$ 中所有类型均不含 TypeParam。故 $F^*$ 的签名（参数类型 + 返回类型）是具体类型，无未解析的 TypeParam。

**关于 body 的处理**：算法 Mono 步骤 5 中 $body$ 直接 clone，未替换。这意味着 $body$ 内部若显式引用 TypeParam（例如 `let x: T = ...`），则在后续类型检查阶段才被处理。这是**工程差距**（见 §8.4 局限 L3），不影响签名层面的健全性，但意味着 body 内部的类型参数解析依赖于后续类型检查 pass。$\square$

### 4.2 定理 M2（编译期复杂度）

**定理 M2**：每个实例化点的编译期时间复杂度为 $O(|T|)$，其中 $|T|$ 是模板签名（参数类型 + 返回类型）的语法大小。

**前置条件**：与 M1 相同。

**证明**：

逐项分析算法 Mono 的开销：

1. **步骤 1（构造 $\sigma$）**：遍历 $\vec{\tau}$，$O(m)$，其中 $m = |\vec{p}|$。由于 $m \leq |T|$（每个参数至少占一个语法节点），故 $O(m) \subseteq O(|T|)$。

2. **步骤 2（替换 ret）**：由性质 3.1，$\text{subst}(ret, \sigma)$ 的复杂度正比于 $|ret|$（递归访问每个语法节点一次，每个节点 $O(1)$ HashMap 查询）。$|ret| \leq |T|$，故 $O(|ret|) \subseteq O(|T|)$。

3. **步骤 3（替换 params）**：类似步骤 2，$\sum_j |param_j| = |T| - |ret| \leq |T|$，故 $O(|T|)$。

4. **步骤 4（mangling）**：遍历 $\vec{\tau}$ 拼接字符串，每个类型的 `Display` 长度 $O(|\tau_i|)$，总计 $O(\sum_i |\tau_i|) \subseteq O(|T| + |\vec{\tau}|) = O(|T|)$。

5. **步骤 5（去重检查）**：`self.functions.iter().any(|f| f.name == mangled_name)` 是线性扫描，复杂度 $O(N)$，其中 $N = |\text{Functions}|$。

> **关键观察**：步骤 5 的 $O(N)$ **不**依赖于 $|T|$，而是依赖于已实例化函数总数。这是工程实现的非最优之处（可用 HashMap 降到 $O(1)$，见 §9.2 未来工作）。但在 Tenth v0.3.3 的典型规模下（$N < 1000$），$O(N)$ 仍是可接受的常数。

**综合**：步骤 1-4 总计 $O(|T|)$，步骤 5 是 $O(N)$。若忽略去重检查（或视为常数），则每实例化点的复杂度为 $O(|T|)$。$\square$

**推论 M2.1**：若 $K$ 个实例化点的签名大小总和为 $S = \sum_{i=1}^{K} |T_i|$，则总编译期开销为 $O(S + K \cdot N)$。

### 4.3 定理 M3（二进制体积膨胀上界）

**定理 M3**：设程序中有 $K$ 个泛型函数实例化点，每个实例化点 $i$ 的函数体大小为 $|B_i|$，则二进制体积膨胀上界为 $O(\sum_{i=1}^{K} |B_i|)$。

**前置条件**：去重检查（算法 Mono 步骤 5）正确，即相同 mangled 名的实例只生成一次。

**证明**：

由算法 Mono 步骤 5，每个 mangled 名 $name^*$ 最多生成一份函数副本。设实例化点集合为 $\{(F_i, \vec{\tau}_i) \mid i = 1, \dots, K\}$，去重后实际生成的函数集合为 $\{F_{j}^* \mid j = 1, \dots, K'\}$，其中 $K' \leq K$。

每个 $F_j^*$ 的体积贡献为：
- 函数体 $B_j$（直接 clone，未压缩）：$|B_j|$；
- 签名（参数类型 + 返回类型）：$O(|T_j|) \subseteq O(|B_j|)$（假设签名不超过函数体大小）；
- Mangled 名字符串：$O(|name| + \sum |\tau|) = O(|T_j|)$。

故 $|F_j^*| = \Theta(|B_j|)$，总体积膨胀为：

$$
V = \sum_{j=1}^{K'} |F_j^*| = \Theta\left(\sum_{j=1}^{K'} |B_j|\right) \leq \Theta\left(\sum_{i=1}^{K} |B_i|\right)
$$

最后不等式由 $K' \leq K$ 及 $|B_j| \leq \max_i |B_i|$（每个去重后的实例对应某个原始实例）得出。$\square$

**推论 M3.1（最坏情况）**：若 $K$ 个实例化点对应 $K$ 个**不同**的 mangled 名（即无去重发生），且函数体大小均为 $|B|$，则体积膨胀为 $\Theta(K \cdot |B|)$。这是单态化的**固有代价**。

**推论 M3.2（共享单态化的对比）**：若引入共享单态化（如 Rust 的 `#[inline]` + LTO 跨函数去重，或 C++ 的 COMDAT 折叠），体积可降至 $O(\sum |B_i| / r)$，其中 $r$ 是共享率。Tenth **未实现**此优化（见 §9.3）。

### 4.4 定理 M4（表达力对比）

**定理 M4**：以泛型表达力（可表达的程序类）为序，Tenth 泛型严格弱于 Rust trait bound 与 C++ template，严格强于 Java wildcard（在保留类型信息意义上），与"无约束单态化"等价。

为陈述精确，定义表达力序 $\preceq$：$L_1 \preceq L_2$ 当且仅当 $L_2$ 可表达的程序类 $\mathcal{P}(L_2) \supseteq \mathcal{P}(L_1)$。

#### 4.4.1 Tenth vs C++ template

**断言**：Tenth $\prec$ C++ template。

**正向**（Tenth $\preceq$ C++ template）：Tenth 的泛型可平凡翻译为 C++ template——`fn foo<T>(x: T) -> T` 对应 `template<typename T> T foo(T x)`。C++ compiler 接受所有 Tenth 泛型程序。

**反向**（C++ template $\not\preceq$ Tenth）：
- (i) C++ template 支持**非类型模板参数**（NTTP），如 `template<int N>`，Tenth 不支持；
- (i') C++ template 支持**模板模板参数**（template template parameter），Tenth 不支持；
- (ii) C++ template 是图灵完备的（template metaprogramming），可在编译期执行任意计算；Tenth 的实例化是纯替换，无编译期计算能力；
- (iii) C++ concepts 提供约束求解，可在实例化前拒绝不满足约束的类型；Tenth 的 bound 仅记录，无拒绝能力。

故 C++ template 严格强于 Tenth。$\square$

#### 4.4.2 Tenth vs Rust trait bound

**断言**：Tenth $\prec$ Rust trait bound。

**正向**（Tenth $\preceq$ Rust）：Tenth 的泛型可翻译为 Rust 无 bound 的泛型——`fn foo<T>(x: T) -> T` 对应 `fn foo<T>(x: T) -> T`。Rust 接受所有 Tenth 泛型程序（前提是 body 不调用 trait 方法）。

**反向**（Rust $\not\preceq$ Tenth）：
- (i) Rust 的 `T: Clone` bound 在实例化前**求解**——若类型未实现 Clone，编译失败；Tenth 的 bound 不求解，无法在编译期拒绝；
- (ii) Rust trait bound 允许 body 调用 trait 方法（`x.clone()`），并通过求解找到具体实现；Tenth 的 body 中若调用 trait 方法，依赖运行时方法分派（见 [`lower_expr.rs:310-347`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs) MethodCall 处理），而非编译期求解；
- (iii) Rust associated type 通过求解解析具体类型；Tenth 无 associated type；
- (iv) Rust 的 trait bound 支持**泛型方法**（`fn foo<T: Iterator<Item=u8>>()`），Tenth 不支持。

故 Rust trait bound 严格强于 Tenth。$\square$

#### 4.4.3 Tenth vs Java wildcard

**断言**：Tenth 与 Java wildcard 不可简单比较，但在"保留类型信息"意义上 Tenth 更强。

**分析**：
- Java wildcard 通过擦除丢失运行时类型信息，Tenth 通过单态化保留；
- Java wildcard 支持**使用点变体**（`? extends T`、`? super T`），Tenth 不支持变体；
- Java wildcard 通过子typing 规则**部分求解**约束，Tenth 不求解；
- Tenth 单态化产生体积膨胀，Java 擦除不产生但运行时装箱。

**不可比性论证**：
- 存在 Java 程序不可翻译为 Tenth：使用 wildcard 变体的容器（如 `List<? extends Number>`），Tenth 无法表达变体；
- 存在 Tenth 程序不可翻译为 Java：依赖具体类型生成不同代码的泛型（如 `fn zeros<T>() -> Tensor<T>`，Java 擦除后无法生成 `zeros_f32` 与 `zeros_f64` 两个版本）。

故二者不可比。但在"保留类型信息"意义上（即运行时可知泛型实参），Tenth 严格强于 Java。$\square$

#### 4.4.4 表达力序总结

$$
\text{Tenth} \prec \text{C++ template}, \quad \text{Tenth} \prec \text{Rust trait bound}, \quad \text{Tenth} \not\preceq \text{Java wildcard}, \quad \text{Java wildcard} \not\preceq \text{Tenth}
$$

即 Tenth 处于**单态化无求解**的极小点，弱于任何带求解的系统，与 Java 不可比但保留更多信息。

### 4.5 定理 M5（bound 的无害性）

**定理 M5**：`generics_bounds` 字段的存在不影响单态化健全性，即：保留该字段（仅记录不求解）与完全移除该字段，在健全性上等价。

**前置条件**：与 M1 相同。

**证明**：

需证：在保留 `generics_bounds` 字段的情况下，单态化健全性（M1）仍成立。

**关键事实**：算法 Mono 的步骤 1-6 中**完全不引用** `generics_bounds` 字段。具体地：
- 步骤 1（构造 $\sigma$）：仅使用 `template.generics`（参数名列表），不使用 `generics_bounds`；
- 步骤 2-3（替换）：仅使用 $\sigma$，不使用 `generics_bounds`；
- 步骤 5（实例化）：实例化后的 $F^*$ 的 `generics_bounds` 被显式置为空 HashMap（见 [`lower_expr.rs:289`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs) `generics_bounds: std::collections::HashMap::new()`）。

**搜索证据**：对 `tenth/src/` 全代码库执行 grep，`generics_bounds` 出现位置如下：

| 位置 | 用途 |
|------|------|
| `hir.rs:229` | 字段定义 |
| `mod.rs:146` | `build_generics_bounds` 函数定义 |
| `lower_stmt.rs:7` | `use` 导入 |
| `lower_stmt.rs:213, 273, 476` | 注册泛型函数时构造（仅记录 bound） |
| `lower_expr.rs:289` | 实例化时置空 |

**无任何位置读取 `generics_bounds` 做约束求解**。这从实证上证明：`generics_bounds` 字段在当前实现中是**纯记录字段**，对算法 Mono 的行为无影响。

**形式化论证**：设 $P$ 为保留 `generics_bounds` 的程序语义，$P'$ 为完全移除该字段的程序语义。由于算法 Mono 不引用该字段，$P$ 与 $P'$ 在单态化阶段产生相同的 $F^*$（参数类型、返回类型、mangled 名均相同）。由 M1，$P'$ 健全，故 $P$ 亦健全。

**结论**：bound 字段的存在是**未来扩展的占位符**，对当前健全性无害。这为未来引入 trait bound 求解留出余地——可在不破坏 M1 的前提下，逐步加入求解逻辑。$\square$

## 5. Tenth 方案的 Trade-off

### 5.1 优势

#### 5.1.1 简单性

`substitute_type` 函数仅 19 行（见 [`mod.rs:126-144`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/mod.rs)），算法 Mono 仅约 60 行（见 [`lower_expr.rs:252-308`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）。与 Rust chalk solver（数千行）或 C++ concepts 求解（编译器核心模块）相比，Tenth 的实现成本极低。

#### 5.1.2 编译速度

由 M2，每实例化点 $O(|T|)$，无递归求解、无回溯、无不终止风险。这避免了 Rust trait solver 的"编译时间爆炸"问题（[Jung et al. 2021] 报告 chalk 在深度递归时不终止）。

#### 5.1.3 可预测性

实例化行为完全由调用点显式决定——程序员看到 `foo<f32>(x)` 就知道生成了 `foo_f32` 副本，无需理解 trait 求解算法。这对 AI 计算场景（dtype 是显式已知的具体类型）特别合适。

#### 5.1.4 运行时性能

单态化产生的代码是**完全特化**的——无字典查找、无 witness table 分派、无装箱。对张量计算等性能敏感场景，这与 C++ template / Rust 单态化等价，优于 Java 擦除 / Haskell 字典传递。

### 5.2 劣势

#### 5.2.1 体积膨胀

由 M3，二进制体积正比于实例化点数 × 函数体大小。对 AI 计算场景，典型实例化点是 dtype 维度（f32 / f64 / i32 / ...），通常 ≤ 5 种，体积膨胀可接受。但对通用编程场景，体积膨胀可能严重（如对每种容器类型实例化算法库）。

#### 5.2.2 表达力弱

由 M4，Tenth 无法表达 trait bound 求解的场景。具体地：
- 无法在编译期拒绝不满足约束的类型（如 `fn sort<T: Ord>` 无法阻止对无序类型的调用）；
- body 中调用 trait 方法依赖运行时分派，性能可能低于 Rust 编译期求解；
- 无 associated type，无法表达 `Iterator<Item=T>` 这类高阶抽象。

#### 5.2.3 去重检查的工程非最优

算法 Mono 步骤 5 使用线性扫描（`self.functions.iter().any(...)`），复杂度 $O(N)$。在实例化点很多时（$N > 10^4$），这可能成为编译瓶颈。可用 HashMap 降至 $O(1)$（见 §9.2）。

### 5.3 适用场景：AI 计算的 dtype 泛型

Tenth 的设计目标是 AI 计算语言，其泛型主要用途是 **dtype 泛型**：

```tenth
fn zeros<T>(shape: Vec<i64>) -> Tensor<T>
fn matmul<T>(a: Tensor<T>, b: Tensor<T>) -> Tensor<T>
fn adamw<T>(param: Tensor<T>, grad: Tensor<T>, ...)
```

在这一场景下：
- dtype 集合有限（f32 / f64 / i32 / i64 / u8 / bool，约 6 种）；
- 调用点显式（`zeros<f32>(...)`）；
- body 中无 trait 方法调用（dtype 操作通过 native 函数分派，见 [`lower_expr.rs:228-234`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）；
- 体积膨胀可接受（6 种 dtype × N 个泛型函数 = 6N 个副本）。

故 Tenth 的极简方案在 AI 计算场景下是**恰到好处**的——既享受单态化的性能，又避免求解的复杂度。

## 6. 工程实现分析

### 6.1 substitute_type 的实现细节

`substitute_type`（见 [`mod.rs:126-144`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/mod.rs)）是一个**结构递归**函数，对 `Type` 的每个变体做模式匹配：

- **TypeParam**：核心情形，查 HashMap，找到则替换，未找到则原样返回（支持部分替换语义）；
- **Ref / MutRef**：单子类型，递归替换内部；
- **Tensor**：递归替换 dtype（dims 不替换，因为 dims 是形状信息，非类型参数）；
- **Array**：递归替换元素类型；
- **Generic**：递归替换 base 和 args（支持高阶泛型，如 `Vec<T>` → `Vec<f32>`）；
- **其他（Base / Struct / Unknown 等）**：直接 clone，无 TypeParam 可替换。

**设计观察**：
1. `Tensor` 的 `dims` 不参与替换——这是合理的，因为 dims 在 Tenth 中是 shape 信息（运行时数据），非类型参数；
2. `Generic` 类型支持嵌套替换，但 Tenth 当前未在泛型实参中嵌套泛型（如 `Vec<Vec<T>>`），故此分支主要用于 `Tensor<T>` 这类构造。

### 6.2 实例化点的处理

实例化点在 `lower_expr.rs` 的 `GenericCall` 分支处理（见 [`lower_expr.rs:252-308`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）。完整流程：

1. **模板查找**：`self.generic_funcs.get(&func_name)` 从泛型函数表取出模板（注意是 `HashMap<String, HirFnDef>`，见 [`mod.rs:22`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/mod.rs)）；
2. **类型实参转换**：`type_args = generics.iter().map(|ta| Type::from_annotation(ta)).collect()`，将 AST 的 `TypeAnnotation` 转为 HIR 的 `Type`；
3. **替换映射构造**：按位置对应 `template.generics` 与 `type_args`；
4. **签名替换**：`substitute_type` 应用到 `return_type` 和 `params`；
5. **Mangling**：`fold(func_name, |acc, ty| format!("{}_{}", acc, ty))`，用 `_` 拼接；
6. **去重检查**：`self.functions.iter().any(|f| f.name == mangled_name)`；
7. **实例化**：若未实例化，构造 `HirFnDef` 推入 `self.functions`；
8. **调用生成**：生成对 mangled 名的普通 `Call`。

**关键观察**：
- 实例化后的函数 `generics` 字段为 `vec![]`（不再是泛型），`generics_bounds` 为空 HashMap（见 [`lower_expr.rs:288-289`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）——即实例化后的函数是**普通函数**，可被后续编译阶段（VM / WASM / JIT）平凡处理；
- body 直接 clone，不替换——这是工程差距（见局限 L3）。

### 6.3 单态化的代码生成

实例化后的函数被加入 `self.functions`（普通函数表），后续编译阶段（VM bytecode / WASM / JIT）无需感知泛型——它们只看到普通函数。这是单态化的核心优势：**将泛型处理局部化在 HIR lowering 阶段**，下游编译器完全无感知。

## 7. 局限（诚实披露）

> 本章遵循数理部"局限必披露"原则，主动记录理论分析与工程实现的差距。

### 7.1 局限 L1：体积膨胀无共享

**描述**：由 M3，二进制体积正比于 $\sum |B_i|$。Tenth 未实现跨实例化点的代码共享（如 Rust LTO 或 C++ COMDAT 折叠）。

**影响**：在通用编程场景下，若同一泛型函数被多种类型实例化且函数体较大，体积膨胀显著。在 AI 计算场景下，由于 dtype 集合有限（约 6 种），影响可接受。

**缓解建议**：
- 短期：在 mangled 名生成中加入结构哈希，识别相同 body 的实例（保守共享）；
- 长期：引入共享单态化（dyadic monomorphization），见 §9.3。

### 7.2 局限 L2：表达力弱于 trait bound 求解系统

**描述**：由 M4，Tenth 无法在编译期拒绝不满足约束的类型，无法表达 associated type，无法做 trait bound 求解。

**影响**：Tenth 不适合通用编程语言场景（如标准库算法库 `sort`、`group_by` 等需要 trait bound 的场景）。

**缓解建议**：
- 当前：依赖运行时方法分派（见 [`lower_expr.rs:310-347`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）替代 trait 方法求解；
- 未来：在 `generics_bounds` 字段已存在的基础上，引入 trait solver（见 §9.1）。

### 7.3 局限 L3：body 不参与替换

**描述**：算法 Mono 步骤 5 中 `body: template.body.clone()`，body 直接 clone，未对 body 内部的 TypeParam 引用做替换。

**影响**：若 body 中显式出现 `T`（如 `let x: T = ...`），则在后续类型检查阶段处理。这依赖于：
- (a) body 中的 TypeParam 引用能在后续 pass 解析；
- (b) body 中的 TypeParam 与签名中的 TypeParam 同名（clone 保留了原始名字）。

**理论影响**：M1 仅保证**签名层面**的健全性（参数类型 + 返回类型不含 TypeParam），**不**保证 body 层面的健全性。body 健全性依赖后续类型检查 pass。

**实证状态**：在 Tenth v0.3.3 的当前测试集（`cargo test`）中，body 中的 TypeParam 处理由后续 pass 隐式完成，未发现回归。但理论形式化未覆盖此情形。

**改进建议**：将 `substitute_type` 扩展为对 `HirExpr` 的递归替换，确保 body 中的 TypeParam 也在实例化时被替换。这会使 M1 完整覆盖 body。

### 7.4 局限 L4：去重检查非最优

**描述**：算法 Mono 步骤 5 使用线性扫描 $O(N)$，非 HashMap $O(1)$。

**影响**：在大规模实例化（$N > 10^4$）时可能成为编译瓶颈。

**缓解**：将 `self.functions` 改为 `HashMap<String, HirFnDef>` 或维护一个 `HashSet<String>` 索引。这是纯工程优化，不影响理论结论。

### 7.5 局限 L5：Mangling 可能冲突

**描述**：mangled 名用 `_` 拼接类型的 `Display` 字符串（见 [`lower_expr.rs:276-277`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/lower_expr.rs)）。若两个不同类型实参列表的 `Display` 字符串相同（例如自定义类型的 `Display` 实现冲突），可能产生 mangled 名冲突，导致**错误去重**。

**影响**：理论上存在，但 Tenth 当前类型集合有限（Base / Tensor / Struct 等），`Display` 实现可控，未发现实际冲突。

**改进建议**：使用类型的结构哈希或唯一 ID 而非 `Display` 字符串。

### 7.6 局限 L6：M4 的形式化不严格

**描述**：M4 的"表达力序"依赖于直观的"可翻译性"概念，未给出严格的可翻译性定义（如保语义的翻译函数）。

**影响**：M4 的结论（Tenth $\prec$ C++ template 等）在直觉上正确，但形式化不严格——例如，C++ template 的图灵完备性如何严格归约为"表达力更强"未给出形式化证明。

**改进建议**：引入形式化的"翻译保持语义"定义（如 denotational semantics 下的等价性），并基于此重证 M4。这是未来工作的方向。

## 8. 开放问题与未来工作

### 8.1 引入 trait bound 求解的可能性

由 M5，`generics_bounds` 字段的存在对健全性无害，这为引入求解留出余地。可能的路径：

1. **最小求解**：在实例化前检查 `generics_bounds` 中的 bound 是否被满足（即类型是否实现了对应 trait）。这是 Rust pre-2021 trait solver 的最小子集，复杂度 $O(|B|)$（bound 集合大小）。
2. **完整求解**：引入 canonical query 求解器（如 chalk），支持 associated type、泛型方法等。复杂度高，可能不终止。

**建议**：先实现最小求解（路径 1），满足 AI 计算场景的需求；完整求解（路径 2）作为长期目标。

### 8.2 去重检查的 HashMap 优化

将 `self.functions` 改为 `HashMap<String, HirFnDef>` 或维护 `HashSet<String>` 索引，将去重检查从 $O(N)$ 降至 $O(1)$。这是纯工程优化，不影响理论结论，可立即实施。

### 8.3 共享单态化（dyadic monomorphization）

引入跨实例化点的代码共享：
- **保守共享**：识别 body 完全相同的实例（结构哈希），共享代码；
- **激进共享**：将 body 中的 TypeParam 替换为运行时分派（类似 Swift witness table），但保留单态化的签名优化。

**复杂度**：保守共享 $O(\sum |B_i|^2)$（两两比较），激进共享 $O(\sum |B_i|)$ 但引入运行时开销。

### 8.4 body 替换的形式化

将 `substitute_type` 扩展为 `substitute_expr : HirExpr × Subst → HirExpr`，在实例化时替换 body 中的 TypeParam 引用。这会使 M1 完整覆盖 body，消除局限 L3。

### 8.5 表达力序的严格形式化

为 M4 引入严格的"翻译保持语义"定义，基于 denotational semantics 重证表达力序。这需要：
- 定义 Tenth / C++ / Rust / Java 的 denotational semantics；
- 定义翻译函数 $f : \text{Prog}(L_1) \to \text{Prog}(L_2)$；
- 证明 $f$ 保持语义（$\llbracket P \rrbracket = \llbracket f(P) \rrbracket$）。

这是博士级工作，超出本文范围。

## 9. 结论

本文对 Tenth 语言的泛型实例化机制进行了完整的形式化分析与表达力对比。核心结论：

1. **Tenth 泛型是无 bound 求解的单态化**，bound 仅记录于 `generics_bounds` 字段，不参与编译期求解（由全代码库搜索证据与 M5 证明）；
2. **单态化健全性（M1）成立**：所有类型参数在实例化前已被显式确定（限于签名层面，body 是局限 L3）；
3. **编译期复杂度（M2）为 $O(|T|)$ 每实例化点**（去重检查 $O(N)$ 是工程非最优）；
4. **二进制体积膨胀（M3）为 $O(\sum |B_i|)$**，无共享单态化；
5. **表达力（M4）严格弱于 C++ template 与 Rust trait bound，与 Java wildcard 不可比**；
6. **bound 字段对健全性无害（M5）**，为未来扩展留出余地。

Tenth 的极简方案在 AI 计算场景下**恰到好处**——dtype 泛型的有限性、显式性、无 trait 方法调用，使得无求解单态化既享受性能又避免复杂度。但在通用编程场景下，其表达力局限显著。未来工作应优先实现 body 替换（消除 L3）与去重 HashMap 优化（消除 L4），这两项是低成本高收益的改进。
