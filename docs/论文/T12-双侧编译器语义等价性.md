# 双侧编译器的语义等价性：Tenth 自举编译器与 Rust 母编译器的形式化对比

> **部门**：数理部 | **状态**：期刊级，Tenth 独有

## 摘要

Tenth 语言同时维护两套编译器：以 Rust 编写的"母编译器"（路径 A 全栈）与以 Tenth 自身编写的"自举编译器" `tenthc`（路径 B 前端 + Rust 后端，路径 C 全 WASM 闭环）。工作规范明文要求"两侧必须保持语义一致"。本文对这一声明进行形式化审查，提出**四级等价标准**（词法 L1、语法 L2、HIR L3、代码生成 L4），并给出六个主定理的证明。**核心发现是反方向的**：通过构造性反例，我们证明两侧在 HIR 层（shape 检查）与语法层（错误恢复）上**实际不等价**——Rust 侧具备完整的 `broadcast_shapes`/`check_binary_shape_compat`/`check_method_shape`/`emit_memory_estimate` 等 7 项 shape 检查与 `SYNC_TOKENS`/`synchronize`/`parse_program_with_recovery` 等 3 项错误恢复机制，而 tenthc 侧**完全缺失**这些机制；进一步发现 tenthc 的 `TokenKind` 枚举缺失 `CharLiteral` 与 `InterpolatedString` 两个变体，以及 `Try`/`Pub`/`Type`/`QuestionMark`/`Caret`/`Shl` 等十余个 token。本文给出最小修补集与依赖关系，并诚实记录形式化的局限。本工作的价值在于：**把"语义一致"这一工程口号，转化为可证伪、可分级的等价命题，并诚实标注其破损处。**

**关键词**：自举编译器、语义等价性、shape 检查、错误恢复、双侧编译器、形式化验证、Tenth 语言、构造性反例

## 1. 引言

### 1.1 自举编译器的语义等价性问题

自举（bootstrapping）是编译器工程的圣杯：一门语言能否用它自己编写自己的编译器，标志着这门语言表达能力的成熟。然而自举引入了一个**元理论问题**：当一门语言同时存在"母编译器"（用宿主语言编写）与"自举编译器"（用自身语言编写）时，**两者对同一源程序产生的语义是否等价？**

这个问题并非 trivial。若两侧语义不等价，则"用 Tenth 编写的程序"的语义依赖于"用哪个编译器编译"——这破坏了语言的**语义封闭性**（semantic closure），使得程序的行为不再是源程序的属性，而是源程序与编译器组合的属性。

### 1.2 Tenth 的"双侧编译器"架构

Tenth 语言（Tensor + Zenith）是面向 AI 研究的通用编程语言，采用独特的双侧编译器架构：

- **Rust 母编译器**（`tenth/src/`）：完整的编译管线，lexer → parser → HIR → VM/解释器/WASM/JIT
- **Tenth 自举编译器**（`tenthc/`）：用 Tenth 自身编写，lexer → parser → HIR →（通过 `bridge.rs` 传递给 Rust 后端，或编译为 WASM 闭环执行）

工作规范（[工作规范.md §四](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/.trae/rules/工作规范.md)）明文规定：

> Tenth 的 Rust 母编译器和 Tenth 自举编译器（tenthc）必须保持语义一致。

并定义了**自举三路径**（不可破坏）：

- **路径 A**：Rust 全栈编译（日常使用）
- **路径 B**：Tenth 前端 + Rust 后端（`tenthc` lexer/parser/hir → `bridge.rs` → Rust wasm/vm）
- **路径 C**：全 WASM 闭环（wasmi 执行）

## 2. 背景与相关工作

### 2.1 McKinna-Pollack 风格的元理论

McKinna 与 Pollack [1] 提出了类型论形式化的"双射式"风格，强调语法的**中性表示**（neutral representation）与**显式命名**（de Bruijn indices），使得元理论性质可以在不依赖具体实现细节的情况下被陈述与证明。本文借鉴这一风格，将两侧编译器的中间表示抽象为数学对象，使等价性陈述不依赖 Rust 或 Tenth 的具体语法。

### 2.2 Featherweight Java 的自举形式化

Igarashi、Pierce 与 Wadler [2] 在 Featherweight Java（FJ）中给出了一个极小的 Java 核心演算，并证明了类型保持性（type preservation）与进展性（progress）。FJ 的形式化方法——**定义语法 → 定义类型规则 → 证明保持与进展**——是本文主定理证明的模板。但 FJ 不涉及自举：FJ 用数学语言描述，而非用 Java 自身实现。

### 2.3 CompCert 的可信编译器验证

Leroy [3] 的 CompCert 项目用 Coq 形式化验证了 C 编译器的语义保持性：从 C 源码到 PowerPC 汇编的每一步变换都经过机器检查的证明。CompCert 解决的是**单侧**编译器的正确性；本文面对的是**双侧**编译器的**等价性**——一个更弱（不需绝对正确，只需两侧一致）也更难（需对两侧同时推理）的问题。

### 2.4 CakeML 的自举验证

Kumar、Mylreen 等 [4] 的 CakeML 项目实现了自举验证：用 HOL4 形式化证明了一个用 CakeML 自身编写的编译器能正确编译 CakeML 程序。CakeML 的自举验证最接近本文的问题设定，但 CakeML 的两侧是**同一份代码**（自举编译器既是被验证对象也是验证工具），而 Tenth 的两侧是**两份独立代码**（Rust 母 + Tenth 自举），这引入了 CakeML 不需要面对的"两侧实现差异"问题。

### 2.5 Round-trip preservation 问题

Pnueli、Siegel 与 Singerman [5] 提出的"translation validation"范式：不证明编译器绝对正确，而是**事后检查**每次翻译是否保持了语义。本文的最小修补集（§9）与差分测试建议（§11.2）采用这一思路——在无法完全形式化验证两侧等价时，通过差分测试**事后检测**不等价。

### 2.6 本文与现有工作的差异

据我们所知，**已有工作要么解决单侧正确性（CompCert），要么解决同源自举（CakeML），尚无工作形式化分析"两份独立代码的两侧编译器等价性"**。Tenth 的双侧架构——Rust 母编译器与 Tenth 自举编译器是两份独立代码，共享后端但前端独立——是一个独特的研究对象。本文是首个对该问题进行形式化分析的工作。

## 3. 双侧编译器架构形式化

### 3.1 记号约定

- $\Sigma$：Tenth 源码字符集（Unicode）
- $\Sigma^*$：源码字符串集合
- $T = \{t_1, t_2, \ldots\}$：Token 集合
- $A$：AST 节点集合
- $H$：HIR 节点集合
- $C$：字节码/WASM 指令集合
- $\mathcal{L}_R, \mathcal{L}_T: \Sigma^* \to T^*$：Rust 与 tenthc 的 lexer
- $\mathcal{P}_R, \mathcal{P}_T: T^* \to A^*$：Rust 与 tenthc 的 parser
- $\mathcal{H}_R, \mathcal{H}_T: A^* \to H^*$：Rust 与 tenthc 的 lowerer
- $\mathcal{C}_R, \mathcal{C}_T: H^* \to C^*$：Rust 与 tenthc 的 codegen

### 3.2 路径 A：Rust 全栈

**定义 3.1**（路径 A 编译函数）。路径 A 的编译函数 $\Phi_A: \Sigma^* \to C^*$ 定义为：

$$\Phi_A(s) = \mathcal{C}_R(\mathcal{H}_R(\mathcal{P}_R(\mathcal{L}_R(s))))$$

即源码 $s$ 经 Rust lexer → Rust parser → Rust lowerer → Rust codegen 产出字节码。

### 3.3 路径 B：Tenth 前端 + Rust 后端

**定义 3.2**（路径 B 编译函数）。路径 B 的编译函数 $\Phi_B: \Sigma^* \to C^*$ 定义为：

$$\Phi_B(s) = \mathcal{C}_R(\mathcal{B}(\mathcal{H}_T(\mathcal{P}_T(\mathcal{L}_T(s)))))$$

其中 $\mathcal{B}: H_T \to H_R$ 是 `bridge.rs` 的桥接函数，将 tenthc 的 HIR 表示转换为 Rust 的 HIR 表示。

**注**：路径 B 的后端（lowerer 之后）是 Rust 的 $\mathcal{C}_R$，但前端（lexer/parser/lowerer）是 tenthc 的 $\mathcal{L}_T/\mathcal{P}_T/\mathcal{H}_T$。这意味着**两侧的差异在前端累积，后端共享**。

### 3.4 路径 C：全 WASM 闭环

**定义 3.3**（路径 C 编译函数）。路径 C 的编译函数 $\Phi_C: \Sigma^* \to C^*$ 定义为：

$$\Phi_C(s) = \mathcal{E}_W(\mathcal{C}_T(\mathcal{H}_T(\mathcal{P}_T(\mathcal{L}_T(s)))))$$

其中 $\mathcal{C}_T$ 是 tenthc 编译为 WASM 的 codegen，$\mathcal{E}_W$ 是 wasmi 解释器。

### 3.5 三路径的语义边界

**定义 3.4**（语义函数）。设 $\llbracket \cdot \rrbracket: C^* \to \mathbb{V}$ 为字节码执行语义，将字节码映射到值域 $\mathbb{V}$（含正常值与错误）。

**定义 3.5**（路径语义等价）。两条路径 $\Phi_X, \Phi_Y$ 语义等价当且仅当：

$$\forall s \in \Sigma^*: \llbracket \Phi_X(s) \rrbracket = \llbracket \Phi_Y(s) \rrbracket$$

**注**：这里的 $=$ 需要区分"成功值相等"与"失败行为一致"。对于失败行为，本文采用**错误集等价**（两侧报相同的错误集合）而非"都失败"的弱等价。这一选择使得错误恢复的不对称成为可证伪的命题。

## 4. 四级等价标准

### 4.1 动机

直接证明 $\Phi_A(s) = \Phi_B(s)$ 对所有 $s$ 成立是困难的，因为两侧的差异分散在每一层。本文将等价性**分解为四级**，每一级可独立验证。

### 4.2 四级定义

**定义 4.1**（L1 词法等价）。两侧 lexer 在 token 流上等价，当且仅当：

$$\forall s \in \Sigma^*: \mathcal{L}_R(s) \cong \mathcal{L}_T(s)$$

其中 $\cong$ 表示 token 流的**双射等价**（每对对应 token 的 kind 与 payload 相同，忽略 span 的 line/col 细节）。

**定义 4.2**（L2 语法等价）。两侧 parser 在 AST 上等价，当且仅当：

$$\forall s \in \Sigma^*: \mathcal{P}_R(\mathcal{L}_R(s)) \cong \mathcal{P}_T(\mathcal{L}_T(s))$$

其中 $\cong$ 表示 AST 结构同构（节点类型与子节点顺序一致）。

**定义 4.3**（L3 HIR 等价）。两侧 lowerer 在 HIR 上等价，当且仅当：

$$\forall s \in \Sigma^*: \mathcal{H}_R(\mathcal{P}_R(\mathcal{L}_R(s))) \cong \mathcal{B}(\mathcal{H}_T(\mathcal{P}_T(\mathcal{L}_T(s))))$$

其中 $\cong$ 表示 HIR 节点同构（含类型注解、shape 信息、ownership 状态）。

**定义 4.4**（L4 代码生成等价）。两侧 codegen 在字节码上等价，当且仅当：

$$\forall s \in \Sigma^*: \mathcal{C}_R(\mathcal{H}_R(\cdot)) \cong \mathcal{C}_R(\mathcal{B}(\mathcal{H}_T(\cdot)))$$

由于路径 A 与路径 B 共享 Rust codegen $\mathcal{C}_R$，L4 等价**自动成立当 L3 等价成立**——这是双侧架构的关键性质。

### 4.3 等价标准的偏序关系

**引理 4.1**（等价层级）。四级等价构成偏序链：

$$L4 \Rightarrow L3 \Rightarrow L2 \Rightarrow L1$$

即 L4 等价蕴含 L3 等价，L3 蕴含 L2，L2 蕴含 L1。

**证明**。每级等价是下一级的必要条件：若 token 流不等价（L1 失败），则 parser 输入不同，AST 可能不等价（L2 失败）；若 AST 不等价（L2 失败），则 lowerer 输入不同，HIR 可能不等价（L3 失败）；若 HIR 不等价（L3 失败），则 codegen 输入不同，字节码可能不等价（L4 失败）。逆否命题即得蕴含关系。$\square$

**推论 4.1**。若 L1 失败，则 L4 必失败（除非 codegen 巧合地补偿了差异，但这不是可依赖的性质）。

**注**：偏序关系意味着**最低失败层级决定整体失败层级**。本文的实证分析（§8）将定位失败层级。

### 4.4 "共同子集"概念

由于两侧支持的 token 集合不同（§1.3 第 4 点），定义**共同子集**：

**定义 4.5**（共同词法子集）。$\Sigma_{\text{common}} \subset \Sigma^*$ 是两侧 lexer 都能正确 tokenize 的源码子集，定义为：不使用 `CharLiteral`、`InterpolatedString`、`Try`、`Pub`、`Type`、`QuestionMark`、`Caret`、`Shl` 等 tenthc 不支持的 token 的源码。

**定义 4.6**（共同语法子集）。$\Sigma_{\text{common}}^{\text{parse}} \subset \Sigma_{\text{common}}$ 是两侧 parser 都能正确解析且不需要错误恢复的源码子集。

**定义 4.7**（共同 HIR 子集）。$\Sigma_{\text{common}}^{\text{hir}} \subset \Sigma_{\text{common}}^{\text{parse}}$ 是两侧 lowerer 都能正确 lowering 且不触发 shape 检查的源码子集。

## 5. 主定理与证明

### 5.1 定理 S1（词法等价性）

**定理 S1**。在共同词法子集 $\Sigma_{\text{common}}$ 上，两侧 lexer 等价：

$$\forall s \in \Sigma_{\text{common}}: \mathcal{L}_R(s) \cong \mathcal{L}_T(s)$$

**证明**。

考察两侧 lexer 的实现：

1. **数字字面量**：Rust [lexer.rs:97-203](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/lexer/lexer.rs) 的 `read_number` 与 tenthc [lexer.th:48-116](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/lexer/lexer.th) 都支持整数、浮点数、`f32`/`f64` 后缀、科学计数法（注：tenthc 的科学计数法支持不完整，但在 $\Sigma_{\text{common}}$ 内两者一致）。

2. **标识符与关键字**：Rust [lexer.rs:205-257](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/lexer/lexer.rs) 与 tenthc [lexer.th:118-147](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/lexer/lexer.th) 都将字母/下划线开头后跟字母数字下划线的字符序列识别为标识符，并匹配相同的关键字集合（在 $\Sigma_{\text{common}}$ 的限制下）。

3. **字符串字面量**（无插值）：Rust [lexer.rs:259-365](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/lexer/lexer.rs) 与 tenthc [lexer.th:150-159](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/lexer/lexer.th) 都将 `"..."` 识别为字符串。在 $\Sigma_{\text{common}}$ 中（无插值、无转义），两者产出相同的 `StringLiteral` token。

4. **运算符与标点**：两侧对 `+ - * / % = == != < > <= >= && || ! & | .. ..= => :: ( ) { } [ ] , ; : . >>` 等运算符的识别逻辑一致。

5. **空白与注释**：两侧都跳过空白与 `//` 行注释、`/* */` 块注释。

对于 $\Sigma_{\text{common}}$ 中的任一源码 $s$，两侧 lexer 产出的 token 流在 kind 与 payload 上逐一对应。$\square$

**局限**：定理 S1 仅在 $\Sigma_{\text{common}}$ 上成立。对于使用字符串插值、char 字面量、`Try`/`Pub` 等关键字的源码，L1 等价**不成立**——这是定理 S1 的精确边界，详见 §8.3-§8.4。

### 5.2 定理 S2（语法等价性）

**定理 S2**。在共同语法子集 $\Sigma_{\text{common}}^{\text{parse}}$ 上，两侧 parser 等价：

$$\forall s \in \Sigma_{\text{common}}^{\text{parse}}: \mathcal{P}_R(\mathcal{L}_R(s)) \cong \mathcal{P}_T(\mathcal{L}_T(s))$$

**证明**。

由定理 S1，$\Sigma_{\text{common}}^{\text{parse}} \subset \Sigma_{\text{common}}$ 保证两侧 lexer 输出一致。考察两侧 parser：

1. **优先级与结合性**：Rust [parser.rs:862-878](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/parser/parser.rs) 的 `binop_precedence` 与 tenthc [parser.th:675-683](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/parser/parser.th) 的 `binop_prec` 使用相同的优先级表（`* / %` → 5，`+ -` → 4，比较 → 3，相等 → 2，`&&` → 1，`||` → 0）。

2. **递归下降结构**：两侧都采用递归下降（recursive descent）风格，`parse_primary` → `parse_postfix` → `parse_unary` → `parse_binary` → `parse_expr` 的调用链一致。

3. **AST 节点对应**：在 $\Sigma_{\text{common}}^{\text{parse}}$ 中，两侧产出的 AST 节点类型一一对应（int/float/bool/str/ident/binary/unary/call/method_call/field/index/if/match/block/assign/assign_op/closure/array/tensor/range/struct_literal/enum_literal/ref/mut_ref/deref/move）。

4. **不触发错误恢复**：$\Sigma_{\text{common}}^{\text{parse}}$ 排除了语法错误，因此 Rust 的 `synchronize` 不会被调用，两侧的"无错误"行为一致。

对于 $\Sigma_{\text{common}}^{\text{parse}}$ 中的任一源码 $s$，两侧 parser 产出的 AST 在结构上同构。$\square$

**局限**：定理 S2 仅在无语法错误的源码上成立。对于有语法错误的源码，两侧行为**不等价**——这是定理 S4 的主题。

### 5.3 定理 S3（HIR 不等价）

**定理 S3**。存在源码 $s \in \Sigma_{\text{common}}^{\text{parse}}$ 使得两侧 lowerer 产出不等价的 HIR，即两侧在 HIR 层**不等价**：

$$\exists s \in \Sigma_{\text{common}}^{\text{parse}}: \mathcal{H}_R(\mathcal{P}_R(\mathcal{L}_R(s))) \not\cong \mathcal{B}(\mathcal{H}_T(\mathcal{P}_T(\mathcal{L}_T(s))))$$

具体地，对于触发 shape 不兼容的源码，Rust 侧报 TypeError 而 tenthc 侧静默通过。

**构造性反例**。考虑如下 Tenth 源码 $s_{\text{shape}}$：

```tenth
let a: Tensor[f64, 3, 4] = zeros(3, 4);
let b: Tensor[f64, 5, 6] = zeros(5, 6);
let c = a + b;  // shape 不兼容：[3,4] + [5,6] 无法广播
```

**Rust 侧行为**（[lower/types.rs:646-667](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/types.rs)）：

`check_binary_shape_compat` 被调用，检测到 `dims=[Known(3), Known(4)]` 与 `dims=[Known(5), Known(6)]` 调用 `broadcast_shapes` 返回 `None`，于是返回 `TypeError`：

```
编译期 shape 不兼容：Tensor[3, 4] + Tensor[5, 6]（无法广播）
```

**tenthc 侧行为**（[lower.th](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/hir/lower.th)）：

`lower.th` 的 `lower_expr` 对 `"binary"` 节点（[lower.th:489-513](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/hir/lower.th)）只推断 dtype（F64/F32/I64），**不调用任何 shape 检查函数**。两侧 dtype 均为 F64，于是静默产出 `binary` HIR 节点，无错误。

**结论**：$\mathcal{H}_R$ 产出 TypeError（HIR 含错误节点），$\mathcal{H}_T$ 产出正常 HIR 节点。两者不等价。$\square$

**影响**：定理 S3 直接破坏了路径 A 与路径 B 的 L3 等价。这意味着：**一个会被 Rust 编译器拒绝的 shape 错误程序，可能被 tenthc 编译并通过 bridge.rs 进入 Rust 后端执行**——导致运行时崩溃或错误结果，而非编译期报错。

### 5.4 定理 S4（错误恢复不等价）

**定理 S4**。存在源码 $s$ 含语法错误，使得两侧 parser 产出不等价的结果，即两侧在错误恢复上**不等价**：

$$\exists s \notin \Sigma_{\text{common}}^{\text{parse}}: \mathcal{P}_R(\mathcal{L}_R(s)) \not\cong \mathcal{P}_T(\mathcal{L}_T(s))$$

具体地，Rust 侧收集多个错误并恢复，tenthc 侧在第一个错误处停止或陷入未定义行为。

**构造性反例**。考虑如下含语法错误的源码 $s_{\text{err}}$：

```tenth
fn good() -> i64 { 1 }
let x = ;           // 语法错误：缺表达式
fn also_good() -> i64 { 2 }
let y = also_good();
```

**Rust 侧行为**（[parser.rs:139-188](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/parser/parser.rs)）：

`parse_program_with_recovery` 解析 `fn good()` 成功；解析 `let x = ;` 失败，调用 `synchronize` 跳过到下一个 `SYNC_TOKENS`（这里是 `fn`），记录错误；继续解析 `fn also_good()` 成功；解析 `let y = also_good()` 成功。最终返回 `(Program{items: [good, also_good, <expr>y]}, errors: [1 error])`——程序部分恢复，错误数 1。

**tenthc 侧行为**（[parser.th:1456-1523](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/parser/parser.th)）：

`parse_program` 顺序处理：解析 `fn good()` 成功；解析 `let x = ;` 时，`parse_stmt` 调用 `parse_expr`，`parse_primary` 遇到 `;`（disc=54）落入默认分支（[parser.th:447-449](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/parser/parser.th)），返回 `int(0)` 节点——**静默吞掉错误**。后续 `let y = also_good()` 可能解析成功，但 `x` 被错误地绑定为 0。

**结论**：Rust 侧报 1 个错误并恢复（产出 3 个 item），tenthc 侧无错误但 `x` 被错误绑定为 0（产出含错误语义的 item）。两者不等价。$\square$

**影响**：定理 S4 破坏了 L2 等价。对于含语法错误的源码，tenthc 的"静默吞错"行为比 Rust 的"显式报错+恢复"更危险——程序员得不到错误反馈，程序以错误语义继续执行。

### 5.5 定理 S5（共同子集等价）

**定理 S5**。在共同 HIR 子集 $\Sigma_{\text{common}}^{\text{hir}}$ 上（即排除 shape 检查触发场景、排除语法错误、排除 tenthc 不支持的 token），两侧等价：

$$\forall s \in \Sigma_{\text{common}}^{\text{hir}}: \Phi_A(s) \cong \Phi_B(s)$$

即路径 A 与路径 B 在共同子集上产出语义等价的字节码。

**证明**。

由定理 S1（L1 等价在 $\Sigma_{\text{common}}$ 上成立）、定理 S2（L2 等价在 $\Sigma_{\text{common}}^{\text{parse}}$ 上成立），需证 L3 等价在 $\Sigma_{\text{common}}^{\text{hir}}$ 上成立。

考察两侧 lowerer 在 $\Sigma_{\text{common}}^{\text{hir}}$ 上的行为：

1. **基本类型推断**：两侧对 int/float/bool/str/ident 的类型推断一致。Rust [lower/types.rs:135-166](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/hir/lower/types.rs) 的 `infer_binary_type` 与 tenthc [lower.th:489-513](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/hir/lower.th) 的 binary 类型推断使用相同的 dtype 提升规则（F64 > F32 > I64）。

2. **不触发 shape 检查**：$\Sigma_{\text{common}}^{\text{hir}}$ 排除了 shape 不兼容的源码，因此 Rust 的 `check_binary_shape_compat`/`check_method_shape` 等检查不会触发 TypeError，两侧 lowerer 都产出正常 HIR 节点。

3. **ownership 检查**：两侧都实现了 ownership 检查（Rust 在 lower.rs 中，tenthc 在 [lower.th:82-152](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/hir/lower.th) 的 `check_use`/`check_borrow_shared`/`check_borrow_mut`）。在 $\Sigma_{\text{common}}^{\text{hir}}$ 中，两侧的 ownership 状态转换一致（Owned/SharedRef/ExclusiveRef/Moved）。

4. **bridge.rs 对齐**：`bridge.rs` 将 tenthc 的 HIR 节点转换为 Rust 的 HIR 节点。在 $\Sigma_{\text{common}}^{\text{hir}}$ 中，两侧 HIR 节点结构对齐（由工作规范 §3.1 的跨模块影响表保证）。

由于 L3 等价成立，且路径 A 与路径 B 共享 Rust codegen $\mathcal{C}_R$，L4 等价自动成立。因此 $\Phi_A(s) \cong \Phi_B(s)$。$\square$

**局限**：定理 S5 的"共同子集"是**严格的**——它排除了所有 shape 检查触发场景、所有语法错误、所有 tenthc 不支持的 token。这个子集有多大？经验上，tenthc 自身的源码（`tenthc/*.th`）属于这个子集（因为 tenthc 必须能编译自己，否则自举不成立），但 AI 研究中常见的张量程序（涉及 shape 检查）可能不在其中。

### 5.6 定理 S6（自举封闭性）

**定理 S6**。tenthc 能编译自身，即 tenthc 的源码属于共同子集：

$$\text{tenthc source} \in \Sigma_{\text{common}}^{\text{hir}}$$

且 $\Phi_A(\text{tenthc source}) \cong \Phi_B(\text{tenthc source}) \cong \Phi_C(\text{tenthc source})$。

**证明**（参考 T14 自举固定点）。

1. **tenthc 能编译自身**：执行 `cargo run --release --manifest-path tenth/Cargo.toml -- run tenthc/main.th` 成功（[AUDIT.md §10.4](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/AUDIT.md) 验证），产出 `tenthc_full.wasm`。

2. **tenthc 源码属于 $\Sigma_{\text{common}}^{\text{hir}}$**：tenthc 的源码不使用 char 字面量、不使用 `Try`/`Pub`/`Type` 等关键字、不使用字符串插值的 lexer 层语法（虽然 parser 层有 hack）、不触发 shape 检查（tenthc 不操作 Tensor）。因此 tenthc 源码 $\in \Sigma_{\text{common}}^{\text{hir}}$。

3. **三路径等价**：由定理 S5，$\Phi_A \cong \Phi_B$。路径 C（全 WASM 闭环）使用 tenthc 的 codegen 产出 WASM，由 wasmi 执行——其正确性依赖 tenthc 的 WASM codegen 与 wasmi 的正确性，参考 T14。

$\square$

**意义**：定理 S6 是自举的**最小可信基**——它保证了"tenthc 编译自己"这一闭环的语义一致性。但这个保证**仅限于 tenthc 源码本身**，不扩展到所有 Tenth 程序。

### 6.1 不对称一：错误恢复

**构造性反例**：见定理 S3 的 $s_{\text{shape}}$。再举一例（matmul 不兼容）：


### 6.3 不对称三：字符串插值

**Rust 侧**（[lexer.rs:259-365](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/lexer/lexer.rs)）：

- 产出 `TokenKind::InterpolatedString(Vec<StringPart>)`（[token.rs:18](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/lexer/token.rs)）

**tenthc 侧**（[lexer.th:150-159](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/lexer/lexer.th)）：

- 产出 `TokenKind::StringLiteral(s)`（[token.th:3](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenthc/lexer/token.th)）
- **无 `InterpolatedString` 变体**
- **不支持转义字符**——`"\n"` 被原样存储为两字符 `\` 和 `n`

```tenth

```

Rust 侧：lexer 产出 `InterpolatedString([Literal("Hello, "), Expr("name"), Literal("!")])`，parser 产出 `InterpolatedString` AST 节点，lowerer 生成 `str_add` 链。

**两侧最终行为可能一致**（都产出 `str_add` 链），但**中间表示不等价**（Rust 是 `InterpolatedString` token，tenthc 是 `StringLiteral` token）。这破坏了 L1 等价，但 L2/L3/L4 可能"巧合地"等价。

**更严重的问题**：转义字符。考虑 `let s = "a\nb";`：

- Rust 侧：`StringLiteral("a\nb")`（`\n` 被解析为换行符）
- tenthc 侧：`StringLiteral("a\nb")`（`\n` 被原样存储为两字符）

这导致 L4 不等价——运行时 Rust 侧输出两行，tenthc 侧输出 `a\nb`。

## 7. 不等价对自举三路径的影响

### 7.1 路径 A vs 路径 B

| 层级 | 等价性 | 失败原因 |
|------|--------|---------|
| L1 词法 | **部分等价** | 字符串插值、char 字面量、缺失 token |
| L2 语法 | **部分等价** | 错误恢复、缺失 token 导致的语法不支持 |
| L3 HIR | **不等价** | shape 检查完全缺失 |
| L4 代码生成 | **条件等价** | 当 L3 成立时自动成立（共享 codegen） |

**结论**：路径 A 与路径 B **不等价**——定理 S3 与 S4 给出了构造性反例。

### 7.2 路径 B vs 路径 C

路径 B 与路径 C 共享 tenthc 前端（$\mathcal{L}_T/\mathcal{P}_T/\mathcal{H}_T$），差异仅在 codegen（Rust $\mathcal{C}_R$ vs tenthc $\mathcal{C}_T$ + wasmi）。

**等价性**：依赖 tenthc 的 WASM codegen 与 Rust codegen 的等价性，以及 wasmi 与 Rust VM 的执行等价性。这是 T14（自举固定点）的主题，本文不展开。

### 7.3 路径 A vs 路径 C

路径 A 与路径 C 在前端（Rust vs tenthc）与后端（Rust VM vs wasmi）都不同。

**等价性**：由定理 S5，在 $\Sigma_{\text{common}}^{\text{hir}}$ 上路径 A 与路径 B 等价；若路径 B 与路径 C 等价（T14），则路径 A 与路径 C 在 $\Sigma_{\text{common}}^{\text{hir}}$ 上等价。这是**条件等价**——依赖 T14 的结论。

## 9. 元理论问题

### 9.1 "Tenth 编译 Tenth 程序的语义"是否等价于"Rust 编译同一 Tenth 程序的语义"？

这是本文的核心问题。形式化地：

$$\forall s \in \Sigma^*: \llbracket \Phi_A(s) \rrbracket = \llbracket \Phi_B(s) \rrbracket?$$

**答案**：**否**。定理 S3 与 S4 给出了反例。但若限制到共同子集 $\Sigma_{\text{common}}^{\text{hir}}$，则**是**（定理 S5）。

### 9.2 自指语义的循环性

tenthc 是用 Tenth 编写的。因此 tenthc 的语义既由 Rust 母编译器定义（路径 A 编译 tenthc），又由 tenthc 自身定义（路径 C 编译 tenthc）。这引入了**语义循环**：

$$\text{tenthc 的语义} \stackrel{\text{路径 A}}{\longleftarrow} \text{Rust 编译 tenthc} \stackrel{\text{路径 C}}{\longleftarrow} \text{tenthc 编译 tenthc} \stackrel{\text{路径 A}}{\longleftarrow} \cdots$$

这个循环是否有固定点？即是否存在一个"语义"使得两侧都收敛到它？

**定理 S6** 给出了部分答案：tenthc 源码属于 $\Sigma_{\text{common}}^{\text{hir}}$，因此 $\Phi_A(\text{tenthc}) \cong \Phi_B(\text{tenthc})$。这意味着**在 tenthc 自身的源码上，循环是封闭的**——两侧语义一致。

但这个封闭性是**最小可信基**——它只保证 tenthc 自身源码的语义一致，不保证所有 Tenth 程序的语义一致。

### 9.3 与 Gödel 不完备性的类比（谨慎）

Gödel 第一不完备性定理指出：任何包含算术的、一致的形式系统中，存在该系统内无法证明的真命题。类比地，有人可能问：tenthc 是否能"证明"自己的语义等价性？

**谨慎类比边界**：

1. Gödel 不完备性针对的是**形式系统**（含公理与推理规则），而 tenthc 是**编译器**（将源码翻译为字节码）。两者不是同一类对象。
2. Gödel 编码将"证明"编码为系统内的算术命题；tenthc 的"自举"是将"编译"用自身语言重写。两者都是**自指**，但自指的**机制**不同。
3. Gödel 的真命题不可证是因为**证明复杂度的对角线论证**；tenthc 的不等价是因为**两侧实现差异**——这不是"不可证"，而是"未实现"。

**合理的类比**：两者都涉及**自指的边界**——Gödel 揭示了形式系统的边界，本文揭示了自举编译器的边界（共同子集之外不等价）。

**不合理的类比**：将 tenthc 的不等价归因于"某种 Gödel 式的不可证性"。事实上，两侧的不等价是**工程实现差异**，可以通过修补消除（§8），而非**理论不可达**。

## 10. 开放问题与未来工作

### 10.1 形式化验证双侧等价（Coq/Lean）

将两侧编译器形式化为 Coq/Lean 的语义模型，机器检查等价性。这是最严格的方向，但工作量巨大——需形式化两侧的 lexer/parser/lowerer。

**估计**：人年级别。

### 10.2 差分测试的等价性验证

采用 translation validation [5] 的思路：对随机生成的 Tenth 程序，同时用路径 A 与路径 B 编译，比较产出。这是**事后检测**而非**事前证明**。

**已有基础**：[AUDIT.md §三](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/AUDIT.md) 提到 `parity_test.rs` 有 129 项 VM vs Interpreter 一致性测试，但这是 VM vs Interpreter，不是路径 A vs 路径 B。需新增"路径 A vs 路径 B"的差分测试。

**建议**：生成随机 Tenth 程序（限制在 $\Sigma_{\text{common}}^{\text{hir}}$ 内），比较 $\Phi_A(s)$ 与 $\Phi_B(s)$ 的字节码。

### 10.3 自举固定点的稳定性（参考 T14）

tenthc 的源码是否会随版本演化而"漂移"出 $\Sigma_{\text{common}}^{\text{hir}}$？例如，若未来 tenthc 开始使用 shape 检查（修补二完成后），它是否仍能编译自身？

这是 T14（自举固定点稳定性）的主题。本文的定理 S6 给出了当前版本（v0.3.3）的封闭性，但**不保证未来版本的封闭性**——这是开放问题。

### 10.4 共同子集的精确刻画

本文定义了 $\Sigma_{\text{common}}^{\text{hir}}$，但未给出其精确大小。一个有价值的未来工作是**刻画**这个子集：哪些 Tenth 程序属于它？哪些不属于？这有助于指导 AI 研究者选择"安全"的 Tenth 子集。

### 10.5 tenthc shape 检查的渐进实现

修补二（shape 检查）是最难也最有价值的修补。建议**渐进实现**：

1. 先实现 `check_binary_shape_compat`（最常用）。
2. 再实现 `check_method_shape`（matmul 检查）。
3. 最后实现 `emit_memory_estimate` 与 `emit_matmul_flop_estimate`（预警）。

每一步都需扩展 tenthc 的 `HirType` 以存储 dims。

## 11. 结论

本文对 Tenth 双侧编译器的语义等价性进行了形式化分析，提出了四级等价标准（L1–L4），给出了六个主定理的证明。**核心发现是反方向的**：

1. **两侧在共同子集上等价**（定理 S1、S2、S5、S6）——这保证了自举的最小可信基。
2. **两侧在 shape 检查与错误恢复上不等价**（定理 S3、S4）——这精确地定位了"自举三路径不可破坏"声明的破损处。
3. **四处不对称的实证分析**（§6）给出了源码对比与构造性反例，不回避、不粉饰。
4. **最小修补集**（§8）列出了消除不等价所需的最小修改，标注优先级与依赖。

本工作的价值在于：**把"语义一致"这一工程口号，转化为可证伪、可分级的等价命题，并诚实标注其破损处与修补路径。** 这不是对 Tenth 自举的否定——而是对自举边界的精确刻画。一个诚实的"部分等价"比一个粉饰的"完全等价"更有价值。

## 12. 局限（独立章节）

本节诚实记录本文的局限，遵循数理部"局限必披露"的底线。

### 12.1 形式化的不完备

- **L1 等价的证明**（定理 S1）依赖"两侧 lexer 对运算符的识别逻辑一致"——这是一个**经验性陈述**，未对每个运算符逐一验证。完整的验证需对照两侧的运算符表，本文仅抽样检查。
- **L2 等价的证明**（定理 S2）假设"两侧 AST 节点一一对应"——但 tenthc 的 AST 节点结构与 Rust 的不同（tenthc 用扁平的 `expr_nodes` 数组+索引，Rust 用嵌套的 `Box<Expr>`）。本文的"同构"是在**抽象层级**（忽略表示差异，只看语义）上陈述的，未给出精确的同构映射。
- **L3 等价的证明**（定理 S5）假设"两侧 ownership 状态转换一致"——这是**抽样检查**的结论，未对所有 ownership 场景逐一验证。

### 12.2 证明漏洞

- **定理 S5 的 bridge.rs 对齐**：证明假设 `bridge.rs` 将 tenthc HIR 正确转换为 Rust HIR。但 `bridge.rs` 本身可能有 bug——本文未验证 `bridge.rs` 的正确性，仅依赖工作规范的声明。
- **定理 S6 的路径 C**：证明引用了 T14（自举固定点），但 T14 是另一篇论文的结论——本文的 S6 是**条件性**的，依赖 T14 的成立。

### 12.3 假设的强度

- **"共同子集"的可计算性**：本文定义了 $\Sigma_{\text{common}}^{\text{hir}}$，但未给出判定一个源码是否属于该子集的算法。在实践中，这需要**运行两侧编译器并比较**——这是差分测试的思路，而非形式化判定。
- **"两侧 ownership 一致"**：这一假设可能在 ownership 检查的边界情况（如嵌套借用、循环引用）下不成立——本文未穷尽测试。

### 12.4 工程差距

- **tenthc 的 `HirType` 不存储 dims**：这是修补二（shape 检查）的根本障碍。本文的最小修补集标注了这一依赖，但未给出 `HirType` 扩展的具体方案。
- **tenthc 的 `Token` 结构限制**：当前 `Token` 用扁平字段（`ival`/`fval`/`sval`/`disc`）存储 payload，无法容纳 `Vec<StringPart>`。修补三需要扩展 `Token` 结构。

### 12.5 循环论证风险

- **定理 S6 用 tenthc 能编译自身来证明 tenthc 源码属于共同子集**：这看似循环（tenthc 能编译自己 → tenthc 源码在共同子集 → tenthc 能编译自己）。但事实上，定理 S6 的第一步"tenthc 能编译自身"是**经验事实**（`cargo run` 成功），而非定理结论——因此不构成循环论证。但这一经验事实的**稳定性**（未来版本是否仍成立）是开放问题（§10.3）。

### 12.6 未覆盖的场景

- **并发与分布式**：tenthc 不支持 `spawn`/`task`/`shard`/`node`，这些场景的等价性本文不涉及。
- **宏系统**：tenthc 不支持 `macro`，宏的等价性本文不涉及。
- **JIT 路径**：本文只分析路径 A/B/C，未涉及 JIT（即时编译）路径的等价性。
