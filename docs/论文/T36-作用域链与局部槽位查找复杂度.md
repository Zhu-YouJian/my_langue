## 摘要

本文对 Tenth 语言在两个执行引擎——tree-walk 解释器与栈式字节码 VM——中的变量查找机制进行复杂度分析与形式化建模。Tenth 在两条路径上采用了截然不同的查找策略：(1) **解释器**用 `Vec<HashMap<String, Value>>` 表示作用域链，每次 `resolve_var`/`set_var` 从最内层作用域向外线性扫描（[`tenth/src/runtime/interpreter/mod.rs:277-326`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)），运行期开销为 $O(\text{scopes} \times \text{hash\_lookup})$；(2) **VM** 在编译期把变量名解析为槽位编号，运行期 `Load(slot)`/`Store(slot)` 退化为 `Vec<Value>` 的 $O(1)$ 数组索引（[`tenth/src/runtime/vm.rs:438-446`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/vm.rs)），但编译期的名字解析本身用 `locals.iter().position(|n| n == name)` 线性扫描（[`tenth/src/compile/bytecode.rs:81-89`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)），对长函数体存在平方复杂度风险。此外，VM 路径为了与解释器的闭包 `FnRef` 语义兼容，对每个 `Assign` 在 `Store(slot)` 之后**额外** emit 一条 `StoreGlobal` 把值同步到 `globals: HashMap`，构成"双重存储"。本文给出五个主定理：**定理 L1**（解释器查找复杂度）、**定理 L2**（VM 运行期查找复杂度 $O(1)$）、**定理 L3**（VM 编译期查找复杂度 $O(\text{locals})$ 及平方风险）、**定理 L4**（双重存储的运行期同步开销）、**定理 L5**（与 V8 scope analysis、Lua upvalue、CPython `LOAD_FAST` 的对比定位），并诚实披露若干局限：本文未覆盖 JIT 路径的查找策略、闭包捕获变量的双重存储正确性证明依赖 T22 但本文未重复、`hash_lookup` 在最坏情况下退化为 $O(\text{bucket})$ 但工程上视为 $O(1)$。

**关键词**：变量查找；作用域链；局部槽位；编译期解析；双重存储；复杂度分析；Tenth 语言

## 1. 引言

### 1.1 变量查找：编译期-运行期的核心权衡

变量查找是动态语言运行时最频繁的操作之一——CPython 字节码中 `LOAD_FAST`/`LOAD_NAME` 占据了执行频次的前几名（[PEP 652, CPython eval loop]），V8 Ignition 中 `LdaCurrentContextSlot`/`LdaGlobal` 同样是热路径。如何把"名字 → 值"的解析代价**从运行期移到编译期**是现代 VM 设计的核心议题：

- **CPython 3.x**：编译期区分 `LOAD_FAST`（局部槽位，$O(1)$）、`LOAD_NAME`（帧 f_locals → f_globals → f_builtins 三级字典查找）、`LOAD_GLOBAL`（f_globals → f_builtins 二级字典查找）、`LOAD_DEREF`（闭包单元格 cell，$O(1)$）。**编译期决定查找协议**，运行期执行对应指令。
- **V8 Ignition**：编译期进行 scope analysis，把变量分类为 `LOCAL`、`CONTEXT`（闭包变量，挂在 context 链上）、`GLOBAL`（全局变量），分别生成 `LdaCurrentContextSlot`、`LdaContextSlot`、`LdaGlobal` 指令。**scope analysis 的输出决定了字节码的查找路径**。
- **Lua 5.x**：编译期把局部变量解析为寄存器编号（`LOAD/STORE R(x)`，$O(1)$），把外层局部变量解析为 upvalue（编译期 `GETUPVAL`/`SETUPVAL`，$O(1)$ 数组索引），只有真正的全局变量才走 `_ENV` 表（运行期哈希查找）。**Lua 是"全局部寄存器化"的极端设计**。

Tenth 在这一谱系中处于一个**有趣的中间位置**：编译期已经能把"局部变量"解析为槽位编号（与 CPython `LOAD_FAST`/Lua `R(x)` 类似），但解析过程本身是**线性扫描**而非哈希查找或符号表索引；同时为了与解释器的 `FnRef` 闭包语义兼容，**每次赋值都额外同步到 globals 表**——这是 CPython/V8/Lua 都没有的"双重存储"。

### 1.2 双重存储的工程动因

Tenth VM 在 `Assign` 节点的代码生成中（[`tenth/src/compile/bytecode.rs:179-197`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）执行如下序列：

```rust
Assign { target, value } => {
    self.compile_expr(value)?;
    self.chunk.emit(Op::Dup);
    if let Some(pos) = self.locals.iter().position(|n| n == target) {
        self.chunk.emit(Op::Store(pos));
    } else {
        let pos = self.locals.len();
        self.locals.push(target.clone());
        self.chunk.emit(Op::Store(pos));
    }
    // Also store as global so closure FnRef values can be called by name.
    self.chunk.emit(Op::Dup);
    let gi = self.chunk.add_string(target);
    self.chunk.emit(Op::StoreGlobal(gi));
}
```

每次赋值都 emit `Store(slot)` **之后**额外 emit `Dup` + `StoreGlobal(gi)`，把同一个值同时写入 `locals[slot]` 和 `globals[name]`。注释明确给出工程动因：**"so closure FnRef values can be called by name"**——闭包 `FnRef` 通过名字调用时走 `CallN(name, n)` 路径，VM 在 `globals` 表中按名查找被调用者（详见 T34 §3.2 双协议讨论）。这就形成了**局部值双重存储**：值既在 `locals` 数组中（供同函数内的 `Load(slot)` $O(1)$ 读取），又在 `globals` 表中（供跨函数的 `CallN` 按名查找）。

这种设计的代价是：
- **空间**：每个被赋值的局部变量在 `globals` 表中占一份额外拷贝。
- **运行期时间**：每次 `Assign` 多两条字节码（`Dup` + `StoreGlobal`），其中 `StoreGlobal` 是 `HashMap::insert`——$O(1)$ 平均，但常数不小。
- **正确性**：局部变量在 `locals` 与 `globals` 中的"双视图"必须保持一致，否则闭包按名调用会读到陈旧值。

### 1.3 贡献

本文的贡献为：

1. **形式化建模**：将 Tenth 两种查找机制抽象为数学对象——解释器为"作用域链 $\langle S_0, S_1, \dots, S_{k-1} \rangle$ 上的线性搜索"，VM 为"局部槽位向量 $L$ 上的索引访问 + globals 哈希表 $G$ 上的同步"。
2. **复杂度证明**：给出五个主定理，分别刻画解释器查找、VM 运行期查找、VM 编译期查找、双重存储同步开销、与主流实现对比。
3. **平方复杂度风险分析**：指出 VM 编译期 `locals.iter().position` 在长函数体上的 $O(N^2)$ 风险，给出触发条件与缓解方案。
4. **诚实披露局限**：明确指出形式化未覆盖的场景（JIT 路径、闭包捕获变量的正确性证明依赖 T22、哈希查找的最坏情况）。

## 2. 背景

### 2.1 V8 的 scope analysis

V8 编译器在解析阶段构建 scope 树，进行变量绑定分析（variable binding analysis），把每个变量引用分类为：

- **LOCAL**：当前函数的局部变量，编译为 `LdaCurrentContextSlot` 或寄存器访问。
- **CONTEXT**：外层函数的局部变量被当前闭包捕获，挂在外层 context 对象上，编译为 `LdaContextSlot`（带 context 链深度 + slot 索引）。
- **GLOBAL**：真正全局变量，编译为 `LdaGlobal`（带全局名字 + 反馈向量槽）。

关键特征：(a) 查找协议在编译期**完全决定**，运行期不需要再扫描作用域链；(b) CONTEXT 变量通过 context 链深度 + slot 索引访问，$O(\text{depth})$ 但 depth 是编译期常量；(c) GLOBAL 变量走内联缓存（IC），首次查找后缓存 slot。

### 2.2 Lua 的 upvalue

Lua 5.x 把变量分为三类：

- **局部变量（local）**：编译期分配寄存器 `R(x)`，访问 `R(x)` 是 $O(1)$。
- **upvalue**：外层函数的局部变量被当前闭包引用，编译期分配 upvalue 索引，访问 `GETUPVAL U(x)` 是 $O(1)$ 数组索引。每个 upvalue 在闭包创建时绑定到具体的外层变量（要么是栈上位置，要么是已经"关闭"迁移到堆上的 cell）。
- **全局变量**：通过 `_ENV` 表（默认是 `_G`）按名查找，`GETTABUP` 指令走哈希表。

关键特征：(a) **没有作用域链运行期扫描**——所有查找在编译期已确定为寄存器、upvalue 或全局表查找；(b) upvalue 的关闭语义（closure 关闭后局部变量迁移到堆）是工程巧妙之处，保证了栈上变量的生命周期可以短于闭包。

### 2.3 CPython 的 LOAD_FAST

CPython 3.x 的编译器在符号表分析阶段（`symtable.c`）把每个块作用域中的变量分类为：

- **局部变量**：编译为 `LOAD_FAST slot`，运行期 `frame->f_localsplus[slot]` 直接索引，$O(1)$。
- **单元格变量（cell）**：被嵌套函数捕获的局部变量，编译为 `LOAD_DEREF`，访问 `frame->localsplus[slot]` 指向的 cell 对象，再读 cell 内值，$O(1)$。
- **自由变量（free）**：嵌套函数引用的外层 cell，同样 `LOAD_DEREF`，$O(1)$。
- **全局/内置**：`LOAD_GLOBAL name`，走 `frame->f_globals → frame->f_builtins` 二级字典查找。

CPython 3.11 引入了自适应解释器与内联缓存，`LOAD_GLOBAL` 也带 IC 槽位。关键特征：(a) 局部变量完全槽位化，$O(1)$；(b) 闭包通过 cell 间接层实现，无运行期作用域链扫描。

### 2.4 Tenth 的定位

Tenth 在这一谱系中：

- **VM 路径**与 CPython `LOAD_FAST` 在运行期等价（局部变量 $O(1)$ 槽位访问），但编译期的名字解析用线性扫描而非符号表。
- **解释器路径**与 Python 2 时代的 `LOAD_NAME` 类似（作用域链扫描），但 Tenth 用 `Vec<HashMap>` 而非 CPython 的 `dict` 链。
- **闭包变量访问**与三者都不同：Tenth 不引入 cell/upvalue/context 间接层，而是用 `globals` 表的"双重存储"来让闭包 `FnRef` 按名查找。这是工程简化但带来性能与正确性代价。

## 3. Tenth 两种查找机制形式化

### 3.1 解释器：作用域链

**定义 3.1（作用域链）**：解释器执行状态包含一个作用域向量

$$\Sigma = \langle S_0, S_1, \dots, S_{k-1} \rangle, \quad S_i : \text{String} \rightharpoonup \text{Value}$$

其中 $S_0$ 是全局作用域，$S_{k-1}$ 是当前最内层作用域（[`tenth/src/runtime/interpreter/mod.rs:40`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）。每个 $S_i$ 是 `HashMap<String, Value>`。

**定义 3.2（解释器变量查找）**：对于变量名 $x$，查找操作 $\text{resolve}_I(x, \Sigma)$ 定义为：

$$\text{resolve}_I(x, \Sigma) = \begin{cases} S_i(x) & \text{若存在 } i \text{ 使得 } i = \max\{j : x \in \text{dom}(S_j)\} \\ \bot & \text{否则} \end{cases}$$

实现上是从 $i = k-1$ 向 $i = 0$ 线性扫描（[`tenth/src/runtime/interpreter/mod.rs:277-287`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）：

```rust
pub(super) fn resolve_var(&self, name: &str) -> Option<Value> {
    for scope in self.scopes.iter().rev() {
        match scope.get(name) {
            Some(Value::Shared(rc)) => return Some(rc.borrow().clone()),
            Some(Value::Moved) => return None,
            Some(other) => return Some(other.clone()),
            None => continue,
        }
    }
    None
}
```

**定义 3.3（解释器变量赋值）**：赋值 $\text{set}_I(x, v, \Sigma)$ 在最内层包含 $x$ 的作用域中更新值，若不存在则插入最内层（[`tenth/src/runtime/interpreter/mod.rs:289-326`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）。

### 3.2 VM：局部槽位 + globals 同步

**定义 3.4（VM 编译期状态）**：编译期 `BytecodeCompiler` 维护局部变量名向量

$$L = \langle \ell_0, \ell_1, \dots, \ell_{n-1} \rangle, \quad \ell_i \in \text{String}$$

`L` 是有序的名字→槽位映射（[`tenth/src/compile/bytecode.rs:13`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)），通过线性扫描查找：$\text{pos}_L(x) = \min\{i : \ell_i = x\}$（[`tenth/src/compile/bytecode.rs:83`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）。

**定义 3.5（VM 运行期状态）**：运行期 VM Frame 状态包含

$$\langle \text{locals}: \text{Vec}[\text{Value}], \text{globals}: \text{String} \rightharpoonup \text{Value}, \text{stack}: \text{Vec}[\text{Value}] \rangle$$

`locals` 是值数组（按槽位索引），`globals` 是名字→值哈希表（[`tenth/src/runtime/vm.rs:438-456`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/vm.rs)）。

**定义 3.6（VM 运行期变量读取）**：编译期对 `Var(x)` 节点生成两条互斥路径之一（[`tenth/src/compile/bytecode.rs:81-89`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）：

$$\text{compile}(\text{Var}(x)) = \begin{cases} \texttt{Load}(i) & \text{若 } \text{pos}_L(x) = i \text{ 存在} \\ \texttt{LoadGlobal}(j) & \text{否则，} j = \text{add\_string}(x) \end{cases}$$

运行期 `Load(i)` 是 $O(1)$ 数组索引（`locals.get(i)`），`LoadGlobal(j)` 是 $O(1)$ 平均哈希查找（`globals.get(&name)`）。

**定义 3.7（VM 运行期变量赋值）**：编译期对 `Assign(x, e)` 节点生成代码序列（[`tenth/src/compile/bytecode.rs:179-197`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）：

$$\text{compile}(\text{Assign}(x, e)) = \text{compile}(e) \mathbin{;} \texttt{Dup} \mathbin{;} \texttt{Store}(i) \mathbin{;} \texttt{Dup} \mathbin{;} \texttt{StoreGlobal}(j)$$

其中 $i = \text{pos}_L(x)$（若不存在则新建槽位并 push 到 $L$），$j = \text{add\_string}(x)$。

注意：**`Var(x)` 的读取不需要 `LoadGlobal` 兜底**——只有 `pos_L(x)` 不存在时才走 `LoadGlobal`；而 `Assign(x, e)` 的写入**总是**同时写 `locals[i]` 和 `globals[x]`。这一**非对称性**是双重存储的核心：写入双重，读取择一。

## 4. 主定理与证明

### 4.1 定理 L1（解释器查找复杂度）

**定理 L1**：设解释器作用域链 $\Sigma = \langle S_0, \dots, S_{k-1} \rangle$，变量 $x$ 在最内层命中作用域的索引为 $i^* = \max\{j : x \in \text{dom}(S_j)\}$（若 $x$ 不存在则 $i^* = -1$，查找失败）。则 `resolve_var(x)` 的运行期时间复杂度为

$$T_{\text{resolve}} = O\bigl((k - i^*) \cdot H\bigr)$$

其中 $H$ 是单次 `HashMap::get` 的平均时间（工程上视为 $O(1)$，最坏 $O(|S_i|)$）。最坏情况 $i^* = -1$ 时退化为 $O(k \cdot H)$。

**证明**：

`resolve_var` 实现从 $i = k-1$ 递减到 $i = 0$ 顺序扫描（[`tenth/src/runtime/interpreter/mod.rs:278-285`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）。对每个作用域 $S_i$ 执行一次 `scope.get(name)`，这是 `HashMap::get` 操作，平均复杂度 $O(H)$，其中 $H$ 与哈希冲突程度有关。

- **命中情况**（$i^* \geq 0$）：循环在第 $i^*$ 次迭代返回，扫描了 $k - 1 - i^* + 1 = k - i^*$ 个作用域。总开销：
$$T_{\text{hit}} = \sum_{i=k-1}^{i^*} O(H) = O\bigl((k - i^*) \cdot H\bigr)$$
- **未命中情况**（$i^* = -1$）：循环跑完全部 $k$ 个作用域，每个作用域执行一次哈希查找返回 `None`：
$$T_{\text{miss}} = \sum_{i=k-1}^{0} O(H) = O(k \cdot H)$$

`set_var`（[`tenth/src/runtime/interpreter/mod.rs:305-323`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）的复杂度分析相同：从内层向外扫描，命中即更新，未命中则插入 `current_scope()`。其开销同样为 $O((k - i^*) \cdot H)$。

证毕。$\square$

**推论 L1.1**：若 $x$ 是当前最内层作用域的局部变量（$i^* = k-1$），则 $T_{\text{resolve}} = O(H) = O(1)$（平均）。这是解释器查找的最优情形。

**推论 L1.2**：若 $x$ 是全局变量（$i^* = 0$），则 $T_{\text{resolve}} = O(k \cdot H)$。深度嵌套的函数访问全局变量时性能最差。

### 4.2 定理 L2（VM 运行期查找复杂度）

**定理 L2**：VM 运行期执行 `Op::Load(i)` 或 `Op::Store(i)` 的时间复杂度为 $O(1)$（最坏情况），与函数内局部变量数量 $n$ 无关。

**证明**：

VM 实现如下（[`tenth/src/runtime/vm.rs:438-446`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/vm.rs)）：

```rust
Op::Load(i) => {
    let v = locals.get(i).cloned().unwrap_or(Value::Unit);
    self.stack.push(v);
}
Op::Store(i) => {
    let v = self.stack.pop().unwrap_or(Value::Unit);
    if i >= locals.len() { locals.resize(i+1, Value::Unit); }
    locals[i] = v;
}
```

`locals.get(i)` 是 `Vec<Value>::get`，本质是指针偏移 `base_ptr + i * sizeof(Value)`，常量时间。`locals[i] = v` 同样是常量时间索引赋值。`stack.push`/`stack.pop` 是 `Vec` 的尾部操作，分摊 $O(1)$。

注意 `Store` 中的 `locals.resize(i+1, Value::Unit)` 仅在 $i \geq |L|$ 时触发——这是边界处理（理论上不应发生，因为编译期 `Assign` 已 push 新槽位），其开销为 $O(i+1 - |L|)$，但这是异常路径而非热路径，不计入正常执行开销。

证毕。$\square$

**推论 L2.1**：VM 路径的运行期查找不依赖作用域嵌套深度 $k$ 也不依赖局部变量数 $n$。这与解释器路径的 $O(k \cdot H)$ 形成对比，是 VM 路径的核心性能优势。

**推论 L2.2**：VM 路径的 `LoadGlobal(j)` 是 `HashMap::get`，平均 $O(H)$，与解释器单作用域查找相同。但 VM 只在编译期 `pos_L(x)` 失败时才生成 `LoadGlobal`，因此**闭包内层访问外层局部变量**这一解释器需要 $O((k - i^*) \cdot H)$ 的操作，在 VM 中要么编译为 $O(1)$ 的 `Load(slot)`（如果外层变量已在 $L$ 中），要么编译为 $O(H)$ 的 `LoadGlobal`（如果通过双重存储在 globals 中）。

### 4.3 定理 L3（VM 编译期查找复杂度与平方风险）

**定理 L3**：设函数体内有 $n$ 个 `Var`/`Assign` 节点引用局部变量，编译期 `BytecodeCompiler::locals` 向量的最大长度为 $|L|_{\max}$。则编译期的总查找开销为

$$T_{\text{compile}} = O\bigl(n \cdot |L|_{\max}\bigr)$$

最坏情况下 $|L|_{\max} = \Theta(n)$（每个 `Assign` 引入新变量），导致 $T_{\text{compile}} = O(n^2)$。

**证明**：

每次编译 `Var(x)` 或 `Assign(x, e)` 节点时，编译器执行（[`tenth/src/compile/bytecode.rs:83, 182`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）：

```rust
self.locals.iter().position(|n| n == name)
```

`Vec::iter().position(|n| n == name)` 是线性扫描：从索引 $0$ 到 $|L|-1$ 逐元素比较字符串相等性。最坏情况下扫描整个 $L$，开销 $O(|L|)$。注意字符串相等比较 `String == String` 本身是 $O(\min(|s_1|, |s_2|))$ 的字节比较，但变量名长度通常有上界 $C$（工程上视为常数），故单次比较记为 $O(C) = O(1)$。

设第 $j$ 个变量引用节点（$1 \leq j \leq n$）执行时 `locals` 长度为 $|L|_j$，则单次查找开销 $O(|L|_j)$。总开销：

$$T_{\text{compile}} = \sum_{j=1}^{n} O(|L|_j) \leq \sum_{j=1}^{n} O(|L|_{\max}) = O(n \cdot |L|_{\max})$$

**平方风险触发条件**：考虑如下 Tenth 程序模式

```tenth
fn f() {
    let a0 = 0;
    let a1 = 0;
    let a2 = 0;
    // ...
    let a_{n-1} = 0;
    // 之后的所有引用都是最后一个变量
    a_{n-1}
}
```

第一个 `Assign(a_0, 0)`：$|L|_0 = 0$，扫描失败后 push，开销 $O(0)$。
第二个 `Assign(a_1, 0)`：$|L|_1 = 1$，扫描整个 $L$ 未命中，开销 $O(1)$。
第 $k$ 个 `Assign(a_{k-1}, 0)$：$|L|_{k-1} = k-1$，扫描整个 $L$ 未命中，开销 $O(k-1)$。
最后一个表达式 `a_{n-1}`：$|L|_n = n$，扫描整个 $L$ 命中（在末端），开销 $O(n)$。

总开销：

$$T_{\text{compile}} = \sum_{k=1}^{n} O(k-1) + O(n) = O\bigl(\tfrac{n(n-1)}{2}\bigr) + O(n) = O(n^2)$$

证毕。$\square$

**推论 L3.1（平方风险）**：包含 $n$ 个独立 `let` 绑定加若干后续引用的函数，编译期开销为 $\Theta(n^2)$。对 $n = 1000$ 的函数，约 $10^6$ 次字符串比较，仍在毫秒级；但对 $n = 10^4$ 的极端函数，约 $10^8$ 次比较，可能进入百毫秒级。

**推论 L3.2（无平方风险情形）**：若所有变量引用都在绑定后立即复用（如 `let x = 1; x + x`），则 $|L|_{\max}$ 由变量总数上界决定，但 $n$ 与 $|L|_{\max}$ 的关系由程序结构决定。若一个函数内只有 $m$ 个不同变量、$n$ 次引用，则 $T_{\text{compile}} = O(n \cdot m)$，当 $m \ll n$ 时退化为 $O(n)$。

**缓解方案**：将 `locals: Vec<String>` 替换为 `locals: HashMap<String, usize>`（名字→槽位映射），编译期查找降为 $O(H) = O(1)$ 平均，总开销 $O(n)$。代价是槽位分配顺序不再严格按 push 顺序，但 `Store(slot)`/`Load(slot)` 的运行期语义不变。

### 4.4 定理 L4（双重存储的运行期同步开销）

**定理 L4**：设函数体有 $m$ 个 `Assign` 节点，VM 路径每个 `Assign` 额外 emit `Dup` + `StoreGlobal`。运行期执行每个 `Assign` 的额外开销为

$$T_{\text{extra}} = O(1) + O(H) = O(H)$$

总额外开销 $O(m \cdot H)$，其中 $H$ 是 `HashMap::insert` 的平均复杂度。

**证明**：

`Assign(x, e)` 编译期生成的指令序列（[`tenth/src/compile/bytecode.rs:180-197`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/compile/bytecode.rs)）：

```
compile(e)      ; 求值 e，结果压栈
Dup             ; 复制栈顶（值1）
Store(i)        ; 弹出值1，写入 locals[i]
Dup             ; 复制栈顶（值2）
StoreGlobal(j)  ; 弹出值2，写入 globals[x]
                ; 栈顶剩值3，作为 Assign 表达式的返回值
```

对比"无双重存储"版本的指令序列（假想）：

```
compile(e)      ; 求值 e，结果压栈
Dup             ; 复制栈顶（值1）
Store(i)        ; 弹出值1，写入 locals[i]
                ; 栈顶剩值2，作为 Assign 表达式的返回值
```

双重存储版本多两条指令：`Dup` + `StoreGlobal(j)`。

- `Op::Dup`：`stack.last().cloned()`，$O(1)$ 加上 `Value::clone` 的开销（若 `Value` 是 `Tensor` 则 clone 可能 $O(\text{size})$，但这是 `Value` 类型设计的另一个问题）。
- `Op::StoreGlobal(j)`：`globals.insert(name, v)`，`HashMap::insert` 平均 $O(H)$，最坏 $O(|\text{globals}|)$。

每个 `Assign` 的运行期总开销：$O(1) + O(H) = O(H)$。

总开销：$O(m \cdot H)$。证毕。$\square$

**推论 L4.1（空间开销）**：双重存储使得每个被赋值的局部变量在 `globals` 表中额外占一份拷贝。若函数有 $m$ 个不同的赋值目标，`globals` 表额外占用 $O(m)$ 个条目。注意：同一变量多次 `Assign` 在 `globals` 中只占一个条目（被覆盖）。

**推论 L4.2（与无双重存储对比）**：若无双重存储，`Assign` 只需 `Store(i)`，$O(1)$；双重存储使 `Assign` 退化为 $O(H)$，**性能损失常数因子约为 $H \approx 50$ ns（典型 HashMap 操作）vs. $1$ ns（数组索引）**。

### 4.5 定理 L5（与 V8/Lua/CPython 对比）

**定理 L5**：在变量查找的运行期复杂度上，Tenth VM 路径与 CPython `LOAD_FAST`/Lua `R(x)` 同阶（$O(1)$）；Tenth 解释器路径与 CPython `LOAD_NAME` 同阶（$O(\text{scopes} \cdot H)$）；Tenth 的双重存储在三者中独有，带来 $O(H)$ 的额外 `Assign` 开销。在编译期复杂度上，Tenth 的 $O(|L|)$ 线性查找劣于 V8/Lua/CPython 的 $O(H)$ 符号表查找。

**证明**：

**运行期对比表**：

| 实现 | 局部变量读取 | 局部变量赋值 | 闭包变量读取 | 全局变量读取 |
|------|------------|------------|------------|------------|
| Tenth 解释器 | $O((k-i^*) \cdot H)$ | $O((k-i^*) \cdot H)$ | $O((k-i^*) \cdot H)$ | $O(k \cdot H)$ |
| Tenth VM | $O(1)$ | $O(1) + O(H)$（双重存储） | $O(H)$（经 globals） | $O(H)$ |
| CPython | $O(1)$（`LOAD_FAST`） | $O(1)$（`STORE_FAST`） | $O(1)$（`LOAD_DEREF` 经 cell） | $O(H)$（`LOAD_GLOBAL` 带 IC） |
| Lua | $O(1)$（`R(x)`） | $O(1)$（`R(x)`） | $O(1)$（`GETUPVAL`） | $O(H)$（`GETTABUP`） |
| V8 Ignition | $O(1)$（context slot） | $O(1)$ | $O(\text{depth})$ context 链 | $O(H)$（IC） |

**关键差异**：

1. **闭包变量**：Tenth VM 通过 `globals` 表间接传递，$O(H)$；CPython 通过 cell 间接层，$O(1)$；Lua 通过 upvalue 数组索引，$O(1)$；V8 通过 context 链深度（编译期常量），$O(\text{depth})$。Tenth 的选择是**工程上最简单**（无需引入 cell/upvalue/context 数据结构），但**性能上最差**（每次闭包内访问外层变量走哈希查找）。

2. **双重存储**：Tenth 独有。CPython 的 `STORE_FAST` 不写 `f_globals`；Lua 的 `R(x)` 不写 `_ENV`；V8 的 `StaCurrentContextSlot` 不写全局。Tenth 的双重存储是为了让 `CallN(name, n)` 按名查找闭包 `FnRef` 时能在 `globals` 中找到——这是**用空间换简单性**的工程权衡。

3. **编译期名字解析**：Tenth $O(|L|)$ 线性扫描；CPython $O(H)$ 符号表；Lua $O(H)$ 符号表；V8 $O(H)$ scope 树。Tenth 在编译期有 $O(n^2)$ 风险，其他三者无。

证毕。$\square$

## 5. 两种查找机制的复杂度分析

### 5.1 解释器路径分析

**优势**：

- **简单性**：作用域链直接对应词法嵌套，`push_scope`/`pop_scope` 语义清晰。
- **动态性**：支持 `eval`、`define-variable!` 等运行期添加绑定的操作（虽然 Tenth 当前不支持，但解释器架构允许）。
- **无编译期开销**：变量查找完全在运行期，无编译期线性扫描问题。

**劣势**：

- **运行期开销大**：每次查找 $O((k - i^*) \cdot H)$，深度嵌套时性能急剧下降。
- **HashMap 分配**：每个作用域是独立 `HashMap`，频繁 `push`/`pop` 作用域带来分配开销。

### 5.2 VM 路径分析

**优势**：

- **运行期 $O(1)$**：局部变量读取退化为数组索引，与函数大小、嵌套深度无关。
- **栈局部性好**：`locals` 数组连续内存，CPU 缓存命中率高。
- **指令紧凑**：`Load(i)` 操作数是整数槽位，比字符串操作数小。

**劣势**：

- **编译期 $O(|L|)$**：长函数体上的线性查找有平方风险（定理 L3）。
- **双重存储**：每次 `Assign` 多两条指令，$O(H)$ 额外开销（定理 L4）。
- **闭包语义简化**：闭包内访问外层变量通过 `globals` 间接，性能 $O(H)$ 而非 $O(1)$。

### 5.3 复杂度对比总表

| 操作 | 解释器 | VM（运行期） | VM（编译期） |
|------|--------|------------|------------|
| 局部变量读取 | $O((k-i^*) \cdot H)$ | $O(1)$ | $O(|L|)$ |
| 局部变量赋值 | $O((k-i^*) \cdot H)$ | $O(1) + O(H)$ | $O(|L|)$ |
| 全局变量读取 | $O(k \cdot H)$ | $O(H)$ | $O(|L|)$（编译期确定走 LoadGlobal） |
| 全局变量赋值 | $O(k \cdot H)$ | $O(1) + O(H)$ | $O(|L|)$ |

## 6. 双重存储的工程权衡

### 6.1 双重存储的必要性

Tenth VM 的双重存储源于 `FnRef` 闭包的按名调用机制：

- Tenth 函数值 `Value::FnRef { name, params, return_type }` 只存**名字**而非函数指针（[`tenth/src/runtime/interpreter/mod.rs:252-256`](file:///d:/史蒂夫/Desktop/AI开发新语言：头脑风暴与评估/tenth/src/runtime/interpreter/mod.rs)）。
- 调用 `CallN(name, n)` 时 VM 在 `globals` 表中按名查找被调用者（详见 T34 §3.2）。
- 闭包内捕获外层局部变量时，由于 VM 没有引入 cell/upvalue/context 间接层，最简单的方案是**让所有局部赋值都同时写入 `globals`**，这样闭包通过名字就能访问到最新值。

### 6.2 双重存储的正确性

**不变量 DS（Double Storage）**：对每个 `Assign(x, e)`，运行期执行后 `locals[i] == globals[x]`（其中 $i = \text{pos}_L(x)$）。

这一不变量由代码生成顺序保证：`compile(e) → Dup → Store(i) → Dup → StoreGlobal(j)`。两次 `Dup` 复制的是**同一个值**（来自 `compile(e)` 的求值结果），因此 `locals[i]` 和 `globals[x]` 接收相同的值。

**注意**：此正确性证明仅覆盖**单线程顺序执行**场景。若引入 JIT 并行优化（T9、T33），需要重新审视双重存储的可见性与一致性——这是本文的局限之一。

### 6.3 双重存储的代价

1. **空间**：$O(m)$ 额外 `globals` 条目（$m$ 为不同赋值目标数）。
2. **时间**：每次 `Assign` $O(H)$ 额外开销，比纯 $O(1)$ `Store` 慢约 50 倍。
3. **语义模糊**：`locals` 与 `globals` 的"双视图"使调试器（T6 关系调试器）需要同时显示两份值，增加复杂度。
4. **优化障碍**：JIT 特化（T9）若想消除 `StoreGlobal`，需要证明该变量不被任何闭包 `FnRef` 按名访问——这是非平凡的静态分析。

### 6.4 替代方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| 当前：双重存储 | 简单，闭包按名调用 | $O(H)$ 额外开销 |
| CPython cell | $O(1)$ 闭包访问 | 引入 cell 间接层，数据结构复杂 |
| Lua upvalue | $O(1)$ 闭包访问 | 需要闭包创建时绑定 upvalue |
| V8 context | $O(\text{depth})$ 闭包访问 | 需要 context 对象，GC 复杂 |
| 字节码级 escape analysis | 仅闭包变量双重存储 | 编译器复杂度增加 |

Tenth 当前选择"双重存储"是**编译器简单性优先**的工程权衡。在 Tenth 当前规模（小函数、闭包使用有限）下，性能代价可接受；若未来支持大型项目，应考虑 escape analysis + 选择性双重存储。

## 7. 与 V8/Lua/CPython 对比

### 7.1 编译期名字解析

| 实现 | 数据结构 | 查找复杂度 | 备注 |
|------|---------|----------|------|
| Tenth | `Vec<String>` | $O(|L|)$ | 线性扫描，平方风险 |

Tenth 是唯一用线性扫描的实现。这反映了 Tenth 编译器前端的"教学清晰性优先"设计——`Vec<String>` 比 `HashMap<String, usize>` 更直观，便于阅读 `bytecode.rs`。但代价是 $O(n^2)$ 编译期风险。

### 7.2 运行期变量访问

见定理 L5 的对比表。Tenth VM 在局部变量访问上与 CPython/Lua 同阶（$O(1)$），在闭包变量访问上最差（$O(H)$）。

### 7.3 闭包实现

| 实现 | 闭包数据结构 | 闭包变量访问 |
|------|------------|------------|
| Tenth | `FnRef { name }` 按名调用 | $O(H)$（走 globals） |

Tenth 的"按名调用 + globals 表"是最简化的设计，但牺牲了闭包变量访问性能。

### 7.4 双重存储的对比

| 实现 | 是否双重存储 | 原因 |
|------|------------|------|
| Tenth | 是 | 闭包按名调用兼容 |

| Lua | 否 | upvalue 已解决 |
| V8 | 否 | context 已解决 |

Tenth 是唯一采用双重存储的实现。这是工程简化决策的代价。

## 8. 工程权衡

### 8.1 当前设计的合理性

Tenth 当前的查找机制设计在以下场景下合理：

1. **教学清晰性**：`Vec<String>` 线性扫描比 `HashMap<String, usize>` 更易理解。
2. **小函数为主**：Tenth 标准库与典型测试用例的函数大小在 $n < 100$ 范围，$O(n^2)$ 编译期开销可忽略。
3. **闭包使用有限**：标准库中闭包主要用于高阶函数（`map`/`filter`/`reduce`），双重存储的运行期开销在总执行时间中占比小。

### 8.2 触发性能问题的场景

1. **长函数体**：$n > 10^3$ 个 `let` 绑定的函数，编译期进入 $O(n^2)$ 区间。
2. **热路径赋值**：紧凑循环内大量 `Assign`，双重存储的 $O(H)$ 开销累积。
3. **深度闭包嵌套**：多层闭包访问外层变量，每层都走 `globals` 哈希查找。

### 8.3 优化建议

1. **编译期**：将 `locals: Vec<String>` 替换为 `locals: HashMap<String, usize>`，消除平方风险（定理 L3 缓解方案）。
2. **运行期**：引入 escape analysis，仅对被闭包捕获的变量双重存储，其他变量只 `Store(slot)`。
3. **闭包**：考虑引入 cell/upvalue 间接层，把闭包变量访问从 $O(H)$ 降到 $O(1)$（需重大重构）。
4. **JIT 兼容**：JIT 特化时（T9）应消除不必要的 `StoreGlobal`，但需保证闭包语义正确。

### 8.4 不建议立即优化的场景

1. **小函数**：$n < 100$ 时 $O(n^2)$ 与 $O(n)$ 差异在微秒级，优化收益小于代码复杂度增加。
2. **冷路径赋值**：非热路径的 `Assign` 双重存储开销可忽略。
3. **无闭包的函数**：双重存储的 `globals` 写入是"浪费但不破坏正确性"，可在 profiling 后选择性消除。

1. **`Value::clone` 在 `Dup` 中的开销**：若 `Value` 是 `Tensor`，`clone` 是 $O(\text{size})$。双重存储每次 `Assign` 多一次 `Dup`，对大 Tensor 赋值可能成为瓶颈。本文未深入分析这一开销，留作后续工作。

2. **JIT 路径的查找策略**：Tenth 的 JIT（T9、T33）是否复用 VM 的 `Load(slot)`/`Store(slot)`？还是引入新的寄存器分配？本文未覆盖 JIT 路径，留作 T33 的后续工作。

3. **闭包捕获变量的正确性证明**：定理 L4 的不变量 DS 仅覆盖单线程顺序执行。闭包 `FnRef` 按名调用的可见性证明依赖 T22（Closure 自由变量分析正确性），本文未重复证明。

4. **`hash_lookup` 最坏情况**：本文将 `HashMap::get`/`insert` 视为 $O(1)$ 平均，但最坏情况为 $O(|S_i|)$ 或 $O(|\text{globals}|)$（哈希冲突）。若攻击者构造恶意变量名触发哈希冲突，可能使运行期查找退化为 $O(n)$。Tenth 未启用 `RandomState` 抗哈希攻击，这是潜在安全风险。

5. **`Store` 中的 `locals.resize` 异常路径**：定理 L2 假设 `locals.resize` 不触发，但若编译器有 bug 导致 `i >= |L|`，运行期 `resize` 会触发 $O(i+1 - |L|)$ 开销。这一异常路径的正确性证明需要 T34 的栈卫生不变量，本文未展开。

6. **WASM 路径的查找机制**：T29（HIR 到 WASM）的查找机制是否与 VM 一致？WASM 是否也双重存储？本文未覆盖 WASM 路径。

7. **解释器-VM 等价性**：解释器 $O((k-i^*) \cdot H)$ 与 VM $O(1)$ 的复杂度差异是否影响 T35（解释器-VM 行为等价性）的证明？等价性是**语义**等价而非**性能**等价，但性能差异可能影响超时边界（T34 §4 摊还 deadline）。

---

## 10. 结论

本文对 Tenth 语言在解释器与 VM 两条路径上的变量查找机制进行了形式化建模与复杂度分析。核心结论：

1. **解释器查找复杂度为 $O(\text{scopes} \times H)$**（定理 L1），深度嵌套时性能下降。
2. **VM 运行期查找复杂度为 $O(1)$**（定理 L2），是 VM 路径的核心性能优势。
3. **VM 编译期查找复杂度为 $O(|L|)$**（定理 L3），长函数体上有 $O(n^2)$ 平方风险。
4. **双重存储的运行期同步开销为 $O(H)$ 每次 `Assign`**（定理 L4），是 VM 路径的工程代价。
5. **Tenth 在变量查找上劣于 V8/Lua/CPython**（定理 L5），尤其是闭包变量访问与编译期名字解析。

工程建议：在 Tenth 当前规模下，现有设计可接受；若支持大型项目，应优先优化编译期名字解析（消除平方风险），其次考虑 escape analysis 减少双重存储。本文的形式化结果可直接指导后续优化决策。

## 11. 局限

本文的局限如下，按影响大小排序：

### 11.1 形式化未覆盖 JIT 路径

Tenth 的 JIT（T9、T33）使用 Cranelift 直接生成机器码，可能不经过 `Load(slot)`/`Store(slot)` 字节码指令。JIT 路径的变量查找机制（寄存器分配？栈偏移？）本文未分析。这是最重要的局限——JIT 是性能关键路径，其查找策略可能与 VM 显著不同。

**影响**：定理 L2、L4 不直接适用于 JIT 路径。
**缓解**：T33 的后续工作应分析 JIT 路径的查找机制。

### 11.2 闭包捕获变量的正确性证明依赖 T22

定理 L4 的不变量 DS 证明仅覆盖单次 `Assign` 的"写入一致性"，未证明**多次 `Assign` 后闭包读取的一致性**（即闭包通过 `CallN(name)` 读到的总是最新值）。这需要 T22 的自由变量分析正确性证明作为前置。

**影响**：双重存储的正确性论证不完整。
**缓解**：本文假设 T22 已证明闭包自由变量分析的语义保持，本文聚焦复杂度而非正确性。

### 11.3 `hash_lookup` 视为 $O(1)$ 的工程假设

本文将 `HashMap::get`/`insert` 视为 $O(1)$ 平均，但严格分析需要：
- 哈希函数的雪崩性质（变量名 → 桶分布均匀？）
- 负载因子（`globals` 表的扩容时机）
- 最坏情况（恶意变量名触发冲突）

**影响**：定理 L1、L4 的复杂度陈述在极端情况下可能不成立。
**缓解**：工程上 Rust 标准库 `HashMap` 用 SipHash，对典型变量名分布良好；若启用 `RandomState` 可抗攻击。

### 11.4 `Value::clone` 开销未建模

`Op::Dup` 中 `stack.last().cloned()` 涉及 `Value::clone`。若 `Value` 是 `Tensor`，`clone` 是 $O(\text{size})$，可能远大于 $O(1)$。本文将 `Dup` 记为 $O(1)$ 是简化。

**影响**：定理 L4 的 $O(H)$ 额外开销在大 Tensor 赋值时不准确，实际为 $O(\text{size}) + O(H)$。
**缓解**：T5（编译期内存预估）的后续工作应分析 `Value::clone` 的开销。

### 11.5 未覆盖 WASM 路径

T29（HIR 到 WASM）的变量查找机制本文未分析。WASM 是否双重存储？是否走 `globals`？这些问题需要单独研究。

**影响**：本文结论仅适用于解释器与 VM 路径。
**缓解**：T29 的后续工作应分析 WASM 路径。

### 11.6 `Store` 异常路径未深入

定理 L2 假设 `locals.resize` 不触发，但若编译器 bug 导致触发，开销为 $O(i+1 - |L|)$。这一异常路径的正确性与开销依赖 T34 的栈卫生不变量。

**影响**：定理 L2 在异常路径下不严格成立。
**缓解**：T34 已证明栈卫生不变量保证 `Ret` 后状态恢复，异常路径不影响调用者。

### 11.7 平方复杂度的实际触发阈值未实测

定理 L3 给出 $O(n^2)$ 风险，但实际触发阈值（$n = 1000$？$n = 10000$？）需要 benchmark 实测。本文仅给出理论分析，未提供实测数据。

**影响**：工程建议（§8.3）的优先级判断缺乏实测支撑。
**缓解**：T36 的后续 benchmark 工作应实测不同 $n$ 下的编译时间。
